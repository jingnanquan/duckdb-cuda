# 说明

本文档针对 [6.4后续进展.md](./6.4后续进展.md) 中列出的 5 个问题，逐条给出**实现方案**与**测试方案**。
本文档只做方案设计，代码尚未改动；实施时建议按文中"实现步骤"顺序推进，每步都应先跑通对应"测试方案"再进入下一步。

先明确一个贯穿全部 5 条的**关键设计原则**（后面各条都会引用）：

> **P0：table_index/ColumnBinding 是唯一可靠的匹配键，字符串列名只能在"catalog 名字 ↔ 物理表列"这一层使用一次。**
> `bitmap_join_meta.json` 里的 `pk_table`/`fk_table` 是**表名字符串**（对 `read_parquet` 场景，是不带路径、不带扩展名的文件名，如 `part`/`orders`），只应该在"给定一个 `LogicalGet`，判断它是不是某个 PK/FK 表"这一步使用一次字符串比较；一旦定位到具体的 `LogicalGet::table_index` 和列在该表中的物理列号，后续所有的传播、去重、防冲突，都必须只用 `ColumnBinding{table_index, column_index}` 做等价判断，绝不再用列名字符串（这是第 4 条"同名 `_rowid`"问题的根本解法）。

---

## 现状回顾（起点）

当前代码（`plan_comparison_join.cpp`）里，BHJ 只有一条路径：

```cpp
if (bhj_eligible && BitmapJoinMetaRegistry::Get(context).IsForceBitmapJoin()) {
    auto pk = registry.GetForceResolvedPK();       // 测试专用、硬编码单个 PK
    if (pk != nullptr) {
        hash_join.use_bitmap_join = true;
        hash_join.bitmap_join_resolved.pk = pk;
        hash_join.bitmap_join_resolved.fk = nullptr;
        hash_join.bitmap_join_resolved.build_is_pk_side = true;   // 硬编码
    }
}
```

且 `BitmapJoinExecutor` 的 build/probe key 都是重新对 `cond.right`/`cond.left`（即原始 PK/FK 值列）求值，而不是读取 `_rowid`/`*_ref` 列。下面 5 条都是围绕"去掉这两个硬编码、把 `_rowid`/`*_ref` 真正用起来"展开。

## 条目 1：用 `LoadFromJson` 的真实绑定信息替代 `SetForceResolvedPK`，走"自动路径"进入 BHJ

### 1.1 问题重述

`BitmapJoinMetaRegistry::TryResolve(build_table, build_col, probe_table, probe_col, out)` 已经实现且能正确处理两种朝向，但目前没有任何调用点——只有测试用的 `SetForceResolvedPK`/`GetForceResolvedPK` 被 `plan_comparison_join.cpp` 使用。需要在**不依赖测试强制开关**的前提下，让 `open_bitmap_join=true` 时，普通查询也能命中 BHJ。

### 1.2 根因分析

`TryResolve` 需要的输入是**表名字符串 + 列名字符串**（`build_table`/`build_col`/`probe_table`/`probe_col`），但 `PlanComparisonJoin` 拿到的 `op.conditions[i].left/right` 此时已经是 **`BoundReferenceExpression`**（只有平坦的 `index`，没有表名）。

原因是 `ColumnBindingResolver` 在 `PhysicalPlanGenerator::CreatePlan` 的**最开始**（见 `src/execution/physical_plan_generator.cpp:39`）就把整棵 `LogicalOperator` 树里的 `BoundColumnRefExpression`（带 `ColumnBinding{table_index, column_index}`）全部改写成了扁平的 `BoundReferenceExpression`。`PlanComparisonJoin` 运行在这之后，天然拿不到表名。

要拿到表名，必须在 `ColumnBindingResolver` 跑之前（即 `Optimizer::Optimize` 返回之前）完成"表名解析"，并把解析结果附着在 `LogicalComparisonJoin` 节点上，供后面的 `PlanComparisonJoin` 读取。

### 1.3 实现方案

**Step A：新增一个"最后阶段"的 Optimizer 步骤（对应详细设计 §6.6 module M-R 的雏形，先不做完整 rule，只做 resolve）**

- 新文件：`src/optimizer/bitmap_join_resolver.hpp/.cpp`，类 `BitmapJoinResolver : LogicalOperatorVisitor`。
- 在 `src/optimizer/optimizer.cpp::RunBuiltInOptimizers()` 的**最后一步**（在 `JOIN_FILTER_PUSHDOWN` 之后，`Verify`/返回之前）插入：

  ```cpp
  RunOptimizer(OptimizerType::BITMAP_JOIN_RESOLVE, [&]() {
      if (Settings::Get<OpenBitmapJoinSetting>(context)) {   // 关闭时零开销，直接 skip
          BitmapJoinResolver resolver(context);
          resolver.VisitOperator(*plan);
      }
  });
  ```

  需要在 `OptimizerType` 枚举里新增 `BITMAP_JOIN_RESOLVE`（`src/include/duckdb/optimizer/optimizer.hpp` + `MetricsUtils::GetOptimizerMetricByType`），这样开关关闭时该 pass 完全不跑，默认行为零回归（呼应设计文档 N1）。
  之所以放在**最后**：此时 `JoinOrderOptimizer`、`ColumnLifetimeAnalyzer`（生成 `left_projection_map`/`right_projection_map`）、`RemoveUnusedColumns` 都已跑完，join 的左右子树顺序、投影裁剪都已经定型，`BitmapJoinResolver` 看到的就是"即将被 `ColumnBindingResolver` 拍平"之前的最终形态，不会被后续 pass 再改动。

**Step B：表名解析辅助函数**

```cpp
// 给定一个 ColumnBinding，从 plan 根向下 DFS 找到 table_index 匹配的 LogicalGet，
// 返回 (逻辑表名, 该 binding 对应的物理列名)。
optional_ptr<LogicalGet> FindSourceGet(LogicalOperator &root, idx_t table_index);
string ResolveLogicalTableName(LogicalGet &get);      // 见下
string ResolveColumnName(LogicalGet &get, idx_t column_index);  // get.GetColumnName(...)
```

`ResolveLogicalTableName` 需要兼容两种数据源（这是本条相对详细设计 §6.2 的一处补充，原设计只考虑了 catalog 表）：

| 数据源 | 取表名的方式 |
| ------ | ------------ |
| 真实 catalog 表（`CREATE TABLE`） | `get.GetTable()->name` |
| `read_parquet(...)` 等 table function | 从 `get.bind_data` 转成 `MultiFileBindData`，取 `file_list` 的第一个文件路径，`basename` 去掉目录和 `.parquet` 后缀。这与 `add_bitmap_columns.py` 生成 `bitmap_join_meta.json` 时 `pk_table`/`fk_table` 的命名方式完全一致（均来自输出目录下的 `<table>.parquet` 文件名），保证字符串能对上。 |

> 已知限制：如果用户查询里给表起了别名（如 `read_parquet('...part.parquet') p`），我们**不使用别名**，只用文件名——别名只在 binder 阶段存在于 `bind_context`，物理阶段已经丢失，重新捞回来成本高且价值低。这个限制会在 1.4 的测试里显式验证并记录为已知边界。

**Step C：`BitmapJoinResolver::VisitOperator` 核心逻辑**

对每个 `LogicalComparisonJoin`：

```cpp
if (!(op.conditions.size() == 1 &&
      op.conditions[0].comparison == ExpressionType::COMPARE_EQUAL &&
      (op.type == JoinType::INNER || op.type == JoinType::RIGHT_SEMI))) {
    return; // 不是 BHJ 候选，跳过（对应条目2 的静态校验一部分）
}
auto &cond = op.conditions[0];
// cond.left 属于 probe 侧(LHS)，cond.right 属于 build 侧(RHS)—— 与 PhysicalHashJoin 的既有约定一致
auto probe_binding = GetColumnBinding(*cond.left);   // BoundColumnRefExpression 尚未被拍平，直接读 .binding
auto build_binding = GetColumnBinding(*cond.right);
if (!probe_binding || !build_binding) return;        // 条件不是纯列引用（比如有表达式），跳过

auto build_get = FindSourceGet(*op.children[1], build_binding->table_index);
auto probe_get = FindSourceGet(*op.children[0], probe_binding->table_index);
if (!build_get || !probe_get) return;                 // 追不到底层 LogicalGet，跳过（详见条目4的多join场景）

string build_table = ResolveLogicalTableName(*build_get);
string build_col   = ResolveColumnName(*build_get, build_binding->column_index);
string probe_table = ResolveLogicalTableName(*probe_get);
string probe_col   = ResolveColumnName(*probe_get, probe_binding->column_index);

BitmapJoinResolved resolved;
if (BitmapJoinMetaRegistry::Get(context).TryResolve(build_table, build_col, probe_table, probe_col, resolved)) {
    // 把结果挂在 LogicalComparisonJoin 节点本身（需要新增字段，见下）
    op.bhj_hint = make_uniq<BitmapJoinResolved>(resolved);
}
```

**Step D：给 `LogicalComparisonJoin` 增加一个"跨阶段传递"的字段**

```cpp
// logical_comparison_join.hpp
//! BHJ 自动解析结果（module 6.6 雏形）；由 BitmapJoinResolver 在物理规划前填充，
//! PlanComparisonJoin 读取后据此设置 PhysicalHashJoin::use_bitmap_join。
//! 与 conditions 一样，只在 ColumnBindingResolver 跑之前有意义；填充后不再依赖表名，
//! 只保留 BitmapJoinResolved（其内部是指向 registry 里 binding 的指针，与列索引无关，
//! 因此能安全地跨过 ColumnBindingResolver 存活到 PlanComparisonJoin）。
unique_ptr<BitmapJoinResolved> bhj_hint;
```

**Step E：`PlanComparisonJoin` 改为优先读取 `op.bhj_hint`，force 开关降级为"仅测试用的覆盖/短路"**

```cpp
auto &registry = BitmapJoinMetaRegistry::Get(context);
optional_ptr<const BitmapJoinPKBinding> pk;
bool build_is_pk_side = true;
if (bhj_eligible && registry.IsForceBitmapJoin() && registry.GetForceResolvedPK()) {
    // 测试强制路径（保留，用于不依赖 optimizer pass 的白盒单测）
    pk = registry.GetForceResolvedPK();
    build_is_pk_side = true;
} else if (bhj_eligible && op.bhj_hint) {
    // 自动路径（条目1 的正题）
    pk = op.bhj_hint->build_is_pk_side ? op.bhj_hint->pk.get() : nullptr;  // 条目2 展开
    build_is_pk_side = op.bhj_hint->build_is_pk_side;
}
if (pk) {
    hash_join.use_bitmap_join = true;
    hash_join.bitmap_join_resolved.pk = pk;
    hash_join.bitmap_join_resolved.build_is_pk_side = build_is_pk_side;
}
```

### 1.4 测试方案

1. **新增单测**（复用 `test/api/test_bitmap_join_perf.cpp` 的数据集与 `RunOnce` 模式，新建 `test/api/test_bitmap_join_auto_resolve.cpp`）：
   - 用 `CREATE VIEW region AS SELECT * FROM read_parquet('.../region.parquet')`（对 8 张表各建一个同名 VIEW，视图名 = 文件名，天然满足 1.3 的命名约束）。
   - 只执行 `SET open_bitmap_join=true;`，**不调用** `SetForceBitmapJoin`/`SetForceResolvedPK`，跑 `part JOIN lineitem ON p_partkey = l_partkey`。
   - 用 `con.Query("EXPLAIN " + sql)` 抓输出文本，`REQUIRE(explain_output.find("Bitmap Join: yes") != string::npos)`。
   - 校验聚合结果与 `open_bitmap_join=false` 基线一致。
2. **别名负例测试**：同一 join 但表引用写成 `read_parquet('.../part.parquet') AS p`（不建 VIEW，直接内联别名），断言 `EXPLAIN` **不**包含 `Bitmap Join: yes`（验证 1.3 里记录的已知限制生效且不报错、不产生错误结果——安全回退到普通 HJ）。
3. **无 catalog 表的回归**：跑一条与 PK/FK 完全无关的普通 join（如两张没有出现在 `bitmap_join_meta.json` 里的表），确认 `open_bitmap_join=true` 时不受影响、`EXPLAIN` 不包含 BHJ 标记、结果正确——验证新 pass 对无关查询是纯粹的旁路。
4. **开关关闭时零开销验证**：`open_bitmap_join=false` 时，通过 `QueryProfiler`/`EXPLAIN ANALYZE` 确认 `BITMAP_JOIN_RESOLVE` phase 耗时为 0（因为 `Settings::Get` 判断后直接跳过），避免对默认路径引入哪怕微小的额外遍历开销。

## 条目 2：自动判断 `build_is_pk_side`，而不是硬编码 `true`

### 2.1 问题重述

现状：`plan_comparison_join.cpp` 里无条件 `bitmap_join_resolved.build_is_pk_side = true`。需要根据 build 侧/probe 侧实际对应的是 PK 表还是 FK 表，自动决定，并在 PK 不在 build 侧时**正确地不选中 BHJ**（而不是错误地选中后在执行期抛异常）。

### 2.2 根因分析与结论

`BitmapJoinMetaRegistry::TryResolve` 内部已经实现了双朝向探测（见 `bitmap_join_meta.cpp:200-229`）：

- 朝向 1：build=PK、probe=FK → `build_is_pk_side=true`
- 朝向 2：build=FK、probe=PK → `build_is_pk_side=false`

但 `BitmapJoinExecutor` 构造函数目前**只支持 `build_is_pk_side==true`**（见 `bitmap_hash_join_executor.cpp:32-34`，`build_is_pk_side==false` 会直接 `throw NotImplementedException`）。

深入想一下"`build_is_pk_side==false`"到底是什么场景：DuckDB 的 `JoinOrderOptimizer`/`BuildProbeSideOptimizer` 会基于基数估计选择哪一侧做 build（一般选小表）。多数情况下 PK（维度表，行数少）会自然落在 build 侧；但如果统计信息误判、或者 FK 表恰好行数更少，`build_is_pk_side` 就会解出 `false`。

**在 MVP 阶段，`build_is_pk_side==false` 语义上就不该走 BHJ**：BHJ 的核心前提是 *build 侧 key 唯一*（详细设计 §3.4 非目标已明确排除 build 侧不唯一场景）。如果 FK 表被规划成 build 侧，它的 key（外键值）不唯一，bitmap 的"1 rowid ↔ 1 行 payload"模型不成立，不能强行塞进现有 executor（也不该实现"反向 executor"去支持它，那是另一套算法，超出 BHJ 范畴）。

因此结论：**条目2 的正确实现不是"让 executor 支持反向"，而是"让 planner 在探测到 build_is_pk_side==false 时主动放弃 BHJ"**，从而避免——现状潜在的一个隐藏 bug：如果哪天 force 覆盖或后续自动路径遇到 `build_is_pk_side=false`，现状代码会一路把 `use_bitmap_join=true` 设进去，直到运行期在 `BitmapJoinExecutor` 构造函数里才 throw，属于"本该在 planning 期静态拦截的错误，退化成运行期异常"，用户体验差（会导致整条 query 报错，而不是静默回退）。

### 2.3 实现方案

1. **`BitmapJoinResolver`（条目1 Step C）里，只有 `resolved.build_is_pk_side == true` 才设置 `op.bhj_hint`**：

   ```cpp
   BitmapJoinResolved resolved;
   if (registry.TryResolve(build_table, build_col, probe_table, probe_col, resolved)
       && resolved.build_is_pk_side) {
       op.bhj_hint = make_uniq<BitmapJoinResolved>(resolved);
   }
   // else: 静默跳过，回退到普通 HashJoin —— 这里天然覆盖了 build_is_pk_side==false 的场景
   ```

   同时把 `PlanComparisonJoin` 里"读到 hint 就直接用"的逻辑保留 `D_ASSERT(op.bhj_hint->build_is_pk_side)` 作为**双重保险**（防御性编程：即使未来有代码路径绕过 `BitmapJoinResolver` 直接写 `bhj_hint`，也不会把错误配置带进执行期）。

2. **`BitmapJoinExecutor` 构造函数里的 `NotImplementedException` 保留**（不删除）：作为最后一道防线，属于"不可能到达的分支"，一旦真的触发说明 planning 期的静态校验有 bug，应该 fail-fast 而不是静默产生错误结果。

3. **可选扩展（M4/M5，非本条 MVP 范围，仅记录方向）**：如果希望"即使 join order 选了 FK 做 build 侧，也能用上 BHJ"，正确做法是在 `BitmapJoinResolver` 里发现 `build_is_pk_side==false` 且 `join_type==INNER`（可交换）时，**反过来修改物理规划**：交换 `left`/`right` 子树、交换 `left_projection_map`/`right_projection_map`、把 `JoinCondition.left`/`.right` 互换，使 PK 表重新成为 build 侧。这本质上是一个"BHJ 感知的 build/probe 侧选择覆盖"，与 DuckDB 现有 `BuildProbeSideOptimizer` 的职责冲突，需要谨慎排期，列为 §17 Open Question 的后续项，不在本轮实现。

### 2.4 测试方案

1. **单测 `BitmapJoinMetaRegistry::TryResolve` 双朝向**（如果尚无覆盖，补一个纯 C++ 单测 `test/unittest/... /test_bitmap_join_meta.cpp`）：
   - 构造 PK=`t1.pk`、FK=`t2.fk→t1.pk`，分别用 `TryResolve("t1","pk","t2","fk",...)`（期望 `build_is_pk_side=true`）和 `TryResolve("t2","fk","t1","pk",...)`（期望 `build_is_pk_side=false`）验证。
2. **Planner 级负例测试**：构造一个 join，人为让 FK 表变成 build 侧——最简单的方式是**绕过 join order optimizer**，直接用 `PRAGMA disable_optimizer='join_order'` 或者构造基数反常的场景（给 FK 表加极小的 `LIMIT`/子查询使其基数被估得比 PK 表小），确认：
   - `EXPLAIN` 不包含 `Bitmap Join: yes`；
   - 结果依然正确（普通 HashJoin 路径）；
   - 不抛任何异常（尤其验证不会在 `BitmapJoinExecutor` 构造函数里触发 `NotImplementedException`）。
3. **正例回归**：确认条目1 的所有既有测试（build_is_pk_side 恰为 true 的常规场景）在改动后依然全部通过，即"自动判断"没有误伐正常场景。

## 条目 3：build 侧用真正的 `_rowid` 列、probe 侧用真正的 `*_ref` 列（而不是复用 PK/FK 原始值）；新增 filter+projection 场景

### 3.1 问题重述

现状 `BitmapJoinExecutor`（`bitmap_hash_join_executor.cpp:27-79`、`241-270`、`383-414`）里，build 侧的 "rowid" 直接来自对 `cond.right`（PK 原始列值）求值后减 `rowid_offset`；probe 侧同理来自 `cond.left`（FK 原始列值）。这只对 `bitmap_join_meta.json` 里 **`rowid_column == pk_column`**（PK 本身稠密可复用，如 `part.p_partkey`、`customer.c_custkey`）的场景正确；对 `rowid_column == "_rowid"`（PK 不稠密，如 `orders.o_orderkey`，需要预处理脚本另外生成的 `_rowid`/`*_ref` 列）**完全没有用上**，也就是说当前 BHJ 事实上只覆盖了 6.4 数据集里 5/6 个 PK 表，覆盖不了 `orders`（进而覆盖不了 `lineitem ⋈ orders` 这条 Q9/Q10 都会用到的关键 join）。

同时要求新增"带 filter/projection 的 SQL"场景：build 侧或 probe 侧在到达 join 之前经过了 `WHERE`/子查询列裁剪，`_rowid`/`*_ref` 这两个"隐藏列"要能穿透这些算子存活下来。

### 3.2 实现方案

**Step A：区分两种情形，明确各自的实现路径**

| 情形 | 判定条件（在 `BitmapJoinResolved` 里可直接读到） | rowid 取值方式 |
| ---- | ------------------------------------------------ | -------------- |
| 稠密复用（fast path，现状已支持） | `pk->rowid_column == pk->pk_column` | 沿用现状：读 join key 原始值 `- pk->rowid_offset` |
| 独立 `_rowid`/`*_ref` 列（本条新增） | `pk->rowid_column != pk->pk_column`（build 侧），或 `fk->ref_column` 非空（probe 侧） | 直接读取该隐藏列的值，`rowid_offset` 固定为 0（脚本保证 `_rowid`/`*_ref` always 0-based，参见 `bitmap_join_meta.json` 里 `orders` 绑定的 `rowid_offset: 0`） |

两者在 executor 层面统一抽象成"给我一个 build 侧列下标 / probe 侧列下标，我直接当 rowid/ref 用"，区别只在**这个下标是 join key 表达式算出来的临时列，还是 chunk 里现成的物化列**。

**Step B：在 `LogicalGet` 上"强制扫描"隐藏列（仅当情形2需要时）**

延续条目1 的 `BitmapJoinResolver`：在确认 `resolved.build_is_pk_side==true` 后，若 `resolved.pk->rowid_column != resolved.pk->pk_column`：

```cpp
// build_get 是条目1 Step C 定位到的 LogicalGet
auto rowid_col_id = FindColumnIdByName(*build_get, resolved.pk->rowid_column); // 按名字找物理列号，仅此一处用字符串（P0原则）
build_get->AddColumnId(rowid_col_id);              // 见 logical_get.hpp:79，强制把该列纳入扫描输出
ColumnBinding rowid_binding(build_get->table_index, build_get->GetColumnIds().size() - 1);
```

若 `resolved.fk->ref_column` 非空（说明这条 FK 绑定需要走 `*_ref` 列，而不是复用 FK 原值），同理在 `probe_get` 上 `AddColumnId`。

> `rowid_column == pk_column` 时**不做任何 `AddColumnId`**——因为 join key 本身（`cond.right`/`cond.left`）已经在 `LogicalGet` 的正常投影里，天然会被扫描，无需额外处理。这保证 fast path 不产生任何多余 I/O。

**Step C：把新 binding 挂在 `bhj_hint` 上，随 `BitmapJoinResolved` 一起跨越 `ColumnBindingResolver`**

在 `BitmapJoinResolved`（`bitmap_join_meta.hpp`）里新增两个可选字段（注意：这两个字段是"逻辑层的 ColumnBinding"，与 catalog 里的静态 `BitmapJoinPKBinding`/`BitmapJoinFKBinding` 无关，所以不适合放在那两个 struct 里，应该放在 per-join 的 resolve 结果里）：

```cpp
struct BitmapJoinResolved {
    const BitmapJoinPKBinding *pk = nullptr;
    const BitmapJoinFKBinding *fk = nullptr;
    bool build_is_pk_side = true;
    //! 仅当 pk->rowid_column != pk->pk_column 时有效：build 侧隐藏 rowid 列的逻辑 binding
    optional<ColumnBinding> build_rowid_binding;
    //! 仅当 fk->ref_column 非空时有效：probe 侧隐藏 ref 列的逻辑 binding
    optional<ColumnBinding> probe_ref_binding;
};
```

**Step D：`ColumnBindingResolver` 需要"看到"这两个隐藏 binding 才会帮我们拍平成物理下标**

`ColumnBindingResolver` 是一个 `LogicalOperatorVisitor`，它递归访问每个 `LogicalOperator::expressions`/`conditions` 等"官方暴露"的表达式列表来做替换；`bhj_hint` 里裸的 `ColumnBinding` 不在这些列表里，不会被自动处理。两个可选实现方式：

- **方式 A（侵入 `ColumnBindingResolver`，不推荐）**：让它认识 `bhj_hint` 字段，特判处理。侵入官方核心遍历逻辑，风险高，后续升级 DuckDB 版本时容易冲突。
- **方式 B（推荐，零侵入）**：把 `build_rowid_binding`/`probe_ref_binding` **包装成两个真正的 `JoinCondition`-同款表达式**，塞进一个我们自己维护的、`LogicalComparisonJoin` 新增的 `vector<unique_ptr<Expression>> bhj_extra_refs`（内容是 `BoundColumnRefExpression`），并让 `LogicalComparisonJoin::GetExpressions()`（`LogicalOperatorVisitor` 遍历官方 API）把这个 vector 一并暴露出去 —— 这样 `ColumnBindingResolver` 会像处理 `conditions[i].left/right` 一样，原地把 `bhj_extra_refs[k]` 从 `BoundColumnRefExpression` 改写成 `BoundReferenceExpression`，之后我们在 `PlanComparisonJoin` 里读 `bhj_extra_refs[k]->Cast<BoundReferenceExpression>().index` 即可得到物理下标。这条路径完全复用 DuckDB 现有机制，改动面最小。

**Step E：`PhysicalHashJoin`/`BitmapJoinExecutor` 消费新增下标**

`physical_hash_join.hpp` 里 `bitmap_build_rowid_idx`/`bitmap_probe_ref_idx` 两个字段**已经预留**（现状代码里声明了但从未赋值/使用，见 `physical_hash_join.hpp:69-72`），本条把它们真正接上：

- `PlanComparisonJoin`：`hash_join.bitmap_build_rowid_idx = (op.bhj_extra_refs.size() > 0) ? op.bhj_extra_refs[0]->Cast<BoundReferenceExpression>().index : DConstants::INVALID_INDEX;`（probe 侧同理用第二个 slot）。
- `BitmapJoinExecutor::SinkBitmap`：

  ```cpp
  Vector &rowid_vec = (join.bitmap_build_rowid_idx != DConstants::INVALID_INDEX)
                           ? chunk.data[join.bitmap_build_rowid_idx]   // 情形2：直接读物化的 _rowid 列
                           : build_keys.data[0];                       // 情形1：沿用现状 fast path
  const int64_t offset = (join.bitmap_build_rowid_idx != DConstants::INVALID_INDEX) ? 0 : build_rowid_offset;
  ExtractBuildRowidsSwitch(rowid_vec, count, offset, ...);
  ```

  `ProbeBitmap` 对称处理 `bitmap_probe_ref_idx`。

**Step F：filter/projection 穿透**

- `WHERE` 过滤（`LogicalFilter`）：不裁剪列，`AddColumnId` 之后天然穿透，无需额外处理。
- 子查询显式列裁剪（`LogicalProjection`，比如 `SELECT o_orderkey, o_custkey FROM orders WHERE ...`）：如果这个 `LogicalProjection` 就在 `LogicalGet` 和 join 之间、且没有把 `_rowid` 选进 `expressions`，需要在 `BitmapJoinResolver` 里检测到路径上有 `LogicalProjection` 时，主动追加一个 `BoundColumnRefExpression` 引用 `rowid_binding`，得到新的输出列位置，并更新 `rowid_binding` 为"投影之后"的新 binding，再继续往上传播（这正是条目4 要通用化的"传播算法"，条目3 只需要覆盖`最多一层 LogicalProjection` 的场景，完整的多层/跨 join 传播见条目4）。

### 3.3 测试方案

1. **新增单测数据依赖**：`orders`⋈`lineitem`（`o_orderkey = l_orderkey`）是本条的关键场景（`orders` 走情形2 `_rowid`，`lineitem` 走 `l_orderkey_ref`）。在 `test_bitmap_join_perf.cpp` 之外新建 `test/api/test_bitmap_join_rowid_ref.cpp`：
   - Case 1（无 filter/projection）：`SELECT count(*), sum(l_quantity) FROM read_parquet(orders) o JOIN read_parquet(lineitem) l ON o.o_orderkey = l.l_orderkey`。开 `open_bitmap_join` + 走自动路径（条目1），断言 `EXPLAIN` 命中 BHJ，结果与基线一致。
   - Case 2（build 侧带 filter+projection）：`SELECT ... FROM (SELECT o_orderkey, o_custkey FROM read_parquet(orders) WHERE o_orderstatus='O') o JOIN lineitem l ON o.o_orderkey = l.l_orderkey`，验证隐藏 `_rowid` 列穿透 `LogicalProjection` 后依然能命中 BHJ 且结果正确。
   - Case 3（probe 侧带 filter+projection）：对称地在 `lineitem` 一侧加 `WHERE l_shipdate > ...` + 显式列裁剪子查询，验证 `*_ref` 列穿透。
   - Case 4（两侧都有）：build+probe 同时带 filter/projection。
2. **零拷贝/正确性交叉验证**：对每个 case，额外跑一遍"手动 `SetForceResolvedPK`+强制 rowid_column=='_rowid' 路径" vs "自动路径"，确认两者结果一致（排除自动路径本身引入 bug 的可能）。
3. **单元测试 `AddColumnId` 幂等性**：确保多次调用 `BitmapJoinResolver`（比如 `EXPLAIN` 之后又执行一次 query，触发两次 plan 生成）不会重复往 `LogicalGet::column_ids` 里塞两份相同的 `_rowid` 列（否则会导致 chunk 里出现重复列、下标错位）。
4. **`SELECT *` 泄漏检查**：`SELECT * FROM orders o JOIN lineitem l ON ...` 情况下，断言最终结果的列名列表里**不包含** `_rowid`/`*_ref`（验证隐藏列只在中间态存在，不会泄漏到用户可见结果——这条也是条目4"sink 前 projection 删除"的最小单 join 版本）。

## 条目 4：多 join 链路下的 `_rowid`/`*_ref` 传播、同名冲突、以及在 sink 前裁剪

### 4.1 问题重述

当上层 `PhysicalHashJoin` 的 build 侧不再是单表 scan，而是**另一个 join 的输出**（例如 `nation ⋈ customer` 的结果作为 `⋈ orders` 的 build 侧输入）时：

1. 下层 join 必须把 `_rowid`（或 `*_ref`）当作一个"payload 列"继续往上传，即使最终 SQL 输出根本不需要它。
2. 如果链路中出现两张表都需要"名字恰好都叫 `_rowid`"的隐藏列（比如自连接，或多个非稠密 PK 表同时出现在一条链路里），如何避免互相覆盖/错位。
3. 最终结果给到 sink 之前，这些隐藏列必须被裁剪掉，不能出现在用户可见的输出里。

### 4.2 核心结论（先说结果，再展开实现）

> **条目4 不需要"发明"新机制，它是条目1 Step A（`BitmapJoinResolver` 跑在 `ColumnLifetimeAnalyzer`/`RemoveUnusedColumns` 之后）+ 条目3 Step F（沿路径向上追加投影引用）两个机制的自然推广**：把"传播路径"从"最多一层 `LogicalProjection`"扩展成"任意深度、且可能穿过其它 `LogicalComparisonJoin` 节点"。而"同名冲突"在 P0 原则（只用 `ColumnBinding` 比较，不用字符串）下**本来就不存在**——需要做的只是确保实现处处遵守 P0，而不是新增去重逻辑。
> "sink 前裁剪"的结论更简洁：**只要传播算法只把隐藏列追加到"确实需要它的那条路径"上（而不是广播到整棵树），它自然会在"最后一个消费者"之后停止传播，不会到达用户看到的最终输出**——不需要额外插入"裁剪用的 `LogicalProjection`"。下面展开这三点。

### 4.3 实现方案

**Step A：两轮遍历（Two-Pass）算法**

`BitmapJoinResolver` 从"单节点判断"升级为"整棵树的两轮遍历"：

- **Pass 1（自底向上收集需求）**：对树中每个 `LogicalComparisonJoin` 做条目1/2 的判断，得到一组 `(join_node, resolved)`；对每个 `resolved` 中需要隐藏列的一侧（build 的 `_rowid` 或 probe 的 `*_ref`），记录一条"传播任务"：`{origin_get, origin_binding, consumer_join}`。
- **Pass 2（按传播任务执行"沿路径追加投影"）**：对每条传播任务，从 `origin_get` 出发，沿着"谁是 `consumer_join` 的祖先/路径上的中间算子"依次向上处理，直到到达 `consumer_join` 本身的直接子节点为止。路径上会遇到两类算子，处理方式不同：

  | 中间算子 | 处理方式 |
  | -------- | -------- |
  | `LogicalProjection` | 在 `expressions` 末尾追加一个引用当前 `binding` 的 `BoundColumnRefExpression`，得到新列位置，更新 `binding` 为 `{projection.table_index, new_index}`，继续向上 |
  | 另一个 `LogicalComparisonJoin`（即隐藏列要"穿过"一个下层 join 才能到达上层 `consumer_join`） | 判断 `binding` 属于该下层 join 的左子树还是右子树；若该下层 join 的 `left_projection_map`/`right_projection_map`**非空**（说明 `ColumnLifetimeAnalyzer` 已经做过裁剪），把 `binding.column_index` **追加**到对应的 `projection_map` 末尾（这是纯 `vector<idx_t>` 的 push_back，安全、局部、不影响已有下标）；若 `projection_map` 为空（意味着该 join 默认不裁剪、输出左右子树全部列），则什么都不用做——binding 天然已经在输出里。处理完后，`binding` 更新为 `{下层join的 table_index, 该 join 输出侧的新位置}`，继续向上 |
  | 其它算子（`LogicalFilter`/`LogicalLimit`等不改变列集合的算子） | 直接跳过，`binding` 不变 |

  到达 `consumer_join` 后，把最终 `binding` 记录为该 join 的 `bhj_extra_refs`（条目3 Step D 的机制），后续与条目3 完全一致地被 `ColumnBindingResolver` 拍平、被 `PlanComparisonJoin` 读出物理下标。

- **传播的终止性**：一条隐藏列可能同时被多个上层 join 消费（fan-out，例如 `customer._rowid` 同时被"`customer⋈orders`"和理论上另一条链路消费——在树状 join plan 里这种情况其实很少见，因为每张表只出现一次，但同一张 PK 表的 `_rowid` 只会被"引用它作为 FK"的**那一个** join 消费，所以典型场景下 fan-out = 1）。实现时按"该 origin 在 Pass 1 收集到的所有 consumer_join"分别独立传播即可，互不影响（各自的 `binding` 变量是独立的局部状态）。

**Step B："同名冲突"在该算法下为什么不存在**

- `origin_get`→`consumer_join` 全程用 `ColumnBinding{table_index, column_index}` 标识列，`table_index` 是 binder 阶段分配的**全局唯一**编号（哪怕是同一张物理表被 `orders o1 JOIN orders o2` 自连接引用两次，`o1`和`o2`会拿到两个不同的 `table_index`）。
- 唯一用到字符串"`_rowid`"的地方是条目3 Step B 里"按名字在 `LogicalGet` 里找物理列号"（`FindColumnIdByName`），这一步只发生**一次**、且作用域局限于单个 `LogicalGet`（一张表内部列名当然是唯一的），不会跨表比较字符串。
- 因此"两张表都有一列叫 `_rowid`"根本不会在本设计的任何环节产生冲突：它们分别是两个独立的 `ColumnBinding`，追加进两个 join 各自独立的 `bhj_extra_refs`/`projection_map`，物理执行时是 chunk 里两个互不相关的下标。

**Step C：为什么"消费完即止"就等价于"sink 前自动裁剪"**

- 每条传播任务只会被追加到"从 origin 到它的 `consumer_join`"这一条路径上的**中间**算子的 `expressions`/`projection_map`，绝不会碰路径以外、更不会碰 `consumer_join`**之上**的任何算子。
- `consumer_join` 本身作为 `PhysicalHashJoin` 执行时，只在**内部**（`bitmap_build_rowid_idx`/`bitmap_probe_ref_idx`）使用这个隐藏列去建 bitmap/查 bitmap，它不属于 `rhs_output_columns`/`lhs_output_columns`（我们不会把它加进这两个"对外输出"的投影表），所以哪怕它是通过某个下层 join 的 `right_projection_map` 才传上来的，一旦到了 `consumer_join` 这一层，它就"到此为止"，不会继续被下一层 join 或最终投影看到。
- 换言之：**隐藏列的生命周期天然被"追加投影"算法的传播范围精确限定**，不需要额外的"清理"步骤。用户最终 `SELECT` 列表对应的最外层 `LogicalProjection`/`LogicalAggregate` 从始至终没有被本机制触碰过，自然不会包含任何隐藏列。

**Step D：一个需要额外小心的边界**——如果 `consumer_join` 自己又是**另一个**更上层 join 的 build 侧输入（也就是链路继续往上、且上层 join 本身又是一个 BHJ 候选，需要用到 `consumer_join` 输出里的某个真实列做新的 PK/rowid），这属于 Pass 1 里对上层 join 单独产生的**另一条独立传播任务**（`origin_get` 直接就是 `consumer_join`，而不是原始 `LogicalGet`）——Pass 2 的算法对"origin 是 join 还是 get"是一致处理的（origin 是 join 时，直接从它的输出 binding 开始向上找路径，无需特殊 case）。

### 4.4 测试方案

1. **三 join 链路正确性测试**（`test/api/test_bitmap_join_chain.cpp`）：`region ⋈ nation ⋈ customer ⋈ orders`（3 个 BHJ 候选 join：`region-nation`、`nation-customer`、`customer-orders`，后者恰好需要把 `customer._rowid`——注意 `customer` 是稠密复用，不需要 `_rowid`，换成更能验证传播的组合：`nation ⋈ customer ⋈ orders`，其中 `customer⋈orders` 需要 `customer` 的稠密 key 穿过"没有裁剪"的场景，再加一层 `orders ⋈ lineitem` 触发真正的 `_rowid` 传播，因为 `orders` 是 build 侧且需要 `_rowid`，而这个 `_rowid` 要从 `orders` 表一路传到 `orders⋈lineitem` 这个 join——这本身就是链路最末端，不需要跨 join 传播；**更能体现"跨 join 传播"的组合是把 `orders` 放在中间**，比如 `customer ⋈ (orders ⋈ lineitem 的结果里re-引用orders._rowid)`——但 TPCH 语义下 `orders` 不会同时是两个不同 join 的 PK 侧。综合数据集实际约束，选用可行且有代表性的链路：`part ⋈ partsupp`（`part` PK 侧，稠密复用）再 `⋈ supplier`（`supplier` PK 侧，稠密复用）——用两个"都是稠密复用但需要跨 join 传播 payload"的 join 先验证传播机制本身（不依赖 `_rowid` 特化），然后专门再加一个"最内层 `orders⋈lineitem`，`orders._rowid` 需要传给外层聚合"的 case 验证 `_rowid` 特化传播。
   - 断言：`EXPLAIN` 中相关 join 节点全部命中 `Bitmap Join: yes`；聚合结果与基线（`open_bitmap_join=false`）一致；最终结果列名列表不包含 `_rowid`/`*_ref`。
2. **同名冲突压力测试**：`orders o1 JOIN orders o2 ON o1.o_custkey = o2.o_custkey`（人工构造的自连接，两侧各自若需要 `_rowid` 会产生两个"字面同名"的隐藏列），断言：不 crash、不产生下标错位（用一个能反映"列错位就会出错"的聚合，比如 `sum(o1.o_totalprice), sum(o2.o_totalprice)` 并与基线逐值比较）。
3. **`RemoveUnusedColumns`/`ColumnLifetimeAnalyzer` 交叉回归**：在 `open_bitmap_join=false` 时，跑 DuckDB 现有的 `test/sql/optimizer/` 全量回归（尤其是 join 列裁剪相关的 `.test` 文件），确认新 pass 因为被开关短路而**完全不影响**既有优化器行为（防止误改了 `RunBuiltInOptimizers` 的调用顺序导致其它 pass 受影响）。
4. **投影追加幂等性/多次 EXPLAIN 测试**：连续对同一条多 join SQL 调用 `EXPLAIN` 两次（同一个 `Connection`，验证 `PhysicalPlanGenerator` 每次都是从原始 `LogicalOperator` 重新走 `Optimizer::Optimize`，还是会复用/污染 plan cache），确保 `AddColumnId`/`projection_map.push_back` 不会在重复执行时线性增长（每次都应该是一次全新的 clone/copy 后处理，不应该在同一个 plan 对象上叠加多次）。

- stdout 打印一张表：`| Query | Mode | Total(ms) | #HashJoin | #BHJ命中 | 各HashJoin耗时明细 |`。
- 同时写一份 CSV 到 `b_idea/perf/sf5/<query>_<mode>.csv`（呼应详细设计 §6.7.1/§12.3 的产出约定），字段：`query,mode,join_id,build_table_guess,probe_table_guess,is_bhj,rows_out,time_ms`。
- 三种模式:
  - baseline：`open_perfect_join=false, open_bitmap_join=false`
  - perfect：`open_perfect_join=true, open_bitmap_join=false`
  - bitmap：`open_perfect_join=false, open_bitmap_join=true`（走条目1-4 的**自动路径**，不用任何 `SetForce*`，这是与现有 `test_bitmap_join_perf.cpp` 的关键区别——那个测试是白盒强制单 join，这个测试是黑盒端到端）

### 5.3 测试方案（本条本身就是测试基础设施，"测试方案"即验收标准）

1. **正确性（硬性 `REQUIRE`）**：三模式的最终聚合结果（Q5/Q9/Q10 各自的 SELECT 输出，按 ORDER BY 后逐行比较，考虑到官方 TPCH 查询本身自带 `ORDER BY`，可以直接逐行 `REQUIRE` 数值相等/在浮点容差内）必须完全一致，任一不一致都是阻塞性 bug（对应详细设计 §12.4 失败判据）。
2. **BHJ 命中率（软性打印，不作为 CI 失败条件）**：打印每条 query 里"预期可命中 BHJ 的 join 数" vs "实际命中数"（预期数可以人工基于 §4.4 表格先标注，例如 Q5 预期 5/6 个 join 命中，`lineitem` 参与的复合等值条件那个 join 因为不满足"单等值条件"预期不命中）。如果实际命中数低于预期，打印详细原因（哪个 join、`bhj_hint` 为空还是 `build_is_pk_side==false` 还是别的），便于调试，但不 `FAIL` 测试（因为命中率依赖前 4 条是否全部实现到位，允许分阶段提交）。
3. **性能对比（软性打印+日志留存，不作为 CI 硬性门槛，理由同现有 `test_bitmap_join_perf.cpp` 的做法）**：打印 baseline/perfect/bitmap 三者总耗时与相对提升百分比；只在明显异常时（bitmap 比 baseline 还慢超过某个阈值，比如 20%）打印一行 `WARNING`，不 `FAIL`，避免 CI 环境噪声导致 flaky。
4. **测试打 `[.]` 隐藏 tag**（与现有 `test_bitmap_join_perf.cpp` 一致），数据集不存在时静默 skip；需要显式指定测试名才会跑，避免拖慢日常 CI。
5. **与真实 DuckDB（无 bitmap 列）结果交叉验证（如果 `data/tpch_sf5`——不带 `_rowid`/`_ref` 列的原始版本——也存在）**：额外跑一遍完全原始表（不建那些 VIEW，直接读原始 SF5 parquet）的 Q5/Q9/Q10，确认与本测试 baseline 模式结果一致，排除"预处理脚本本身改坏了数据"的可能（这是比 3 种内部模式互相比较更强的正确性锚点）。

## 实施顺序建议与依赖关系

```text
条目1 (自动路径解析) ──┬─► 条目2 (build_is_pk_side 自动判断，在条目1的 pass 里顺带实现)
                        │
                        └─► 条目3 (_rowid/_ref 列注入与消费，单 join 场景)
                                │
                                └─► 条目4 (推广到多 join 链路传播)
                                        │
                                        └─► 条目5 (Q5/Q9/Q10 端到端验收，依赖 1-4 全部落地)
```

- 条目1、2 强耦合，建议合并成一个 PR/一次提交（`BitmapJoinResolver` 一次性把两者都做了，本文档拆开写只是为了对应原始问题清单）。
- 条目3 是条目4 的特例（"路径长度=1层投影"），建议先实现条目3 的最小版本（不做通用传播算法，只做"最多穿过一层 `LogicalProjection`"），跑通测试后再扩展成条目4 的通用两轮遍历算法——这样每一步都有可回归的测试兜底，避免一次性实现一个大而复杂的传播算法导致调试困难（历史教训：6.4 阶段 `BitmapJoinOperatorState` 继承错误导致的 SIGSEGV 调试成本很高，本轮应尽量小步提交）。
- 条目5 的测试基础设施（VIEW 建表、SQL 模板、profiling JSON 解析器）可以提前搭好骨架，先在"预期命中数=0"（因为条目1-4 还没实现）的状态下跑通"正确性对比"部分，作为后续每完成一条就能立刻看到命中率提升的反馈闭环。

## 风险与开放问题（新增，补充详细设计 §16/§17）

| ID | 风险/问题 | 说明 |
| -- | --------- | ---- |
| R-NAME | 表别名/CTE/子查询包装导致 `ResolveLogicalTableName` 找不到底层 `LogicalGet` | 条目1 已知限制，MVP 阶段直接放弃 BHJ（安全回退），不视为 bug |

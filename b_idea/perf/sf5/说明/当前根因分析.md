当前Q10与baseline性能持平
Q5的bitmapjoin用时反而增加。给定以下分析，


根因：bitmap 模式不如 perfect hash join 紧凑

perfect=30ms 用紧凑数组（build_range+1 大小），20% 密度下有效数据占 20%，cache 局部性好
bitmap=94ms 用 750K 行的稀疏数组，同样 20% 密度，但比 perfect 的紧凑数组多了 rowid 间接寻址 + gather 开销
baseline=50ms 普通 hash join 建小哈希表（15万行），也能放进 cache
Q5 的改善方向
核心问题是 payload_columns 按 bitmap_size 分配，不适应低密度场景。三个可能方向：

方向1（最有效）：payload_columns 按实际行数分配 + rowid→index 映射表

用一个 rowid → dense_index 的查找表（或直接用 bitmap 的 popcount），让 payload 按实际行数紧凑存储
Q5 Join 1：从 150MB 降到 5.2MB（可放 L3），gather cache miss 大幅减少
但需要在 probe 时多一步：bitmap hit → rowid → dense_index → payload gather


方向2（简单）：低密度自动回退到 perfect hash join 或普通 hash join

密度 < 阈值（如 30%）时不走 BHJ，走 perfect hash join（Join 2 的 perfect=30ms 比 bitmap=94ms 快 3 倍）
Join 1 也可回退，baseline=145ms 比 bitmap 的 wall-clock 贡献的 ~80ms 增量要好


然而：方向1和方向2都有难点和设计冲突

方向1：需要额外 rowid → dense_index 的映射表，这个映射表应该是用什么数据结构存储？两跳索引查找+额外填充映射表可能增加开销。payload仍然需要硬拷贝，并且修改前后本身都可以放进l3缓存。甚至两跳索引可能引入额外的cache miss

方向2：核心是我们从哪里获取密度信息？？如果bitmap已经构建完再获取是绝对不行的。更别提bitmap阶段额外维护hash表，这是本末倒置了。最差最差情况需要跟perfecthashjoin类似，提前用candoperfect去估计max/min获取大致的密度，看能够走bitmapjoin

# Bitmap-Join（BHJ）SF5 性能根因分析（详细版 · v2）

> 配套原文档：`当前根因分析.md`
> 代码基线：`database/duckdb-cuda`
> 目标：在通读 BHJ 实现与 TPC-H SF5 实测数据后，修正并深化原文档的根因判断，并把优化路线**明确拆成两条**：
> - **模式1（低密度 / 稀疏 build）**：计划期判密度 → `est_density` 标识；初期直接 `bitmapjoin=false` 回退到其它 join；后期再做"轻量 hash 双重映射 + payload 顺序 append"的紧凑表示。
> - **模式B（稠密但 BHJ 仍慢）**：先加"稠密 fast-path 可跳过逐行位测试"，与 perfect hash join 对比；再像模式1 一样思考能否在 payload 复制上优化。

> **实施状态（代码已落地）**：
> - ✅ **4.2 初期方案（模式1 低密度回退）**：已在计划期实现。`plan_comparison_join.cpp` 置 `use_bitmap_join` 前用 `est_density = right.estimated_cardinality / pk->row_count` 判密度，低于 `BHJ_LOW_DENSITY_THRESHOLD`(=0.3) 时置 `bhj_skip_reason = LOW_DENSITY` 并 `pk=nullptr` 回退普通/perfect 哈希 join（force 测试覆盖不受影响）。新增枚举值 `BitmapJoinSkipReason::LOW_DENSITY` 与常量 `BHJ_LOW_DENSITY_THRESHOLD`（`bitmap_join_meta.hpp`），`BitmapJoinSkipReasonToString` 已补 `"low_density"`。
> - ✅ **5.1 稠密 fast-path（模式B 跳过逐行位测试）**：`BitmapJoinExecutor` 新增 `is_build_dense`，`FinalizeBitmap` 用 `global_bitmap.CountValid(bitmap_size) == bitmap_size` 判定；`FillProbeSelection`/`FillProbeSelectionSwitch` 透传该标志，稠密时跳过 `:386` 的逐行位测试。与 perfect 的对比/5.3 零拷贝尚未做。

## 0. TL;DR（结论先行）

1. **真正决定 BHJ probe 代价的是 `payload 工作集 = bitmap_size × RHS 输出列总宽度`**，其中 `bitmap_size` 在 BHJ 中恒等于**整张维度（PK）表行数**（`bitmap_hash_join_executor.cpp:46,56-81`），与 bitmap 填充比例无关。原文档把根因归为"低密度"是**因果倒错**——低密度只是让浪费更夸张，宽 payload 才是主因。
2. **失效模式拆成两类，优化路线各管各的：**
   - **模式1（低密度 / 稀疏 build）**：维度表被上游过滤，bitmap 只填一部分（实测 ~13–20%），payload 仍按全维度行数分配 → 浪费 + gather 散布 → cache miss。对应 Q5 `lineitem↔orders`（1548ms）。**路线 = 计划期判密度 → 初期回退 / 后期紧凑双重映射。**
   - **模式B（稠密但 BHJ 仍慢）**：维度键连续稠密，bitmap 100%，但 BHJ **无条件做逐行位测试**（`bitmap_hash_join_executor.cpp:386`），而 perfect 有稠密 fast-path 跳过 → BHJ 反而慢（Q5 `orders↔customer` 94ms vs perfect 30ms）。**路线 = 稠密 fast-path + 与 perfect 对比 + payload 零拷贝。**
3. **计划期已有足够静态信息做密度/工作集估计**（无需运行时测）：`pk->row_count`、`right.estimated_cardinality`、`join.rhs_output_columns.col_types`。照搬 perfect hash join 的 `CanDoPerfectHashJoin + PerfectHtThresholdSetting` 计划期决策范式即可。
4. **"combine 锁"已解决**（`CombineBitmap` 是 `atomic fetch_or` + `touched_words` 稀疏合并，`:305-333`），瓶颈已转到 build payload 尺寸与 probe gather，本分析只攻后者。

## 1. BHJ 工作原理（代码定位）

决策与接线（`plan_comparison_join.cpp:85-125`）：
- `BitmapJoinResolver` 在优化期把满足条件的 join 标注 `op.bhj_hint`，`PlanComparisonJoin` 在 `pk` 命中时**无条件** `hash_join.use_bitmap_join = true`（`:107-108`），无任何代价判断。
- BHJ 仅支持：单等值、INNER、build 侧为 PK（维度）侧（`bitmap_hash_join_executor.cpp:31-44`）。

Build（`bitmap_hash_join_executor.cpp:31-93, 260-303`）：
- 构造期按 `bitmap_size = resolved.pk->row_count`（**整张维度表行数**）为**每个 RHS 输出列**预分配一个 Vector（`:46, 56-81`）。
- `SinkBitmap`：抽取每个 build 行的 `rowid`，置位本地 bitmap，再把列 scatter 到 `payload_columns[rowid]`（`:280-301`）。定长列 lock-free，变长列加 `build_lock`。
- `CombineBitmap`：各线程本地 bitmap 用 `atomic fetch_or` 合并到全局，只遍历 `touched_words`（`:305-333`）。

Probe（`bitmap_hash_join_executor.cpp:429-485`）：
- 对 probe 每行算 `rowid = key - rowid_offset`，**无条件** `bitmap.RowIsValidUnsafe(rowid)` 位测试（`:386`）。
- 命中后把 LHS 列引用/切片，RHS 列用 `result.data[...].Slice(*payload_columns[i], build_sel_vec, ...)` 按 `rowid` **gather**（`:467-469`）。

对比 perfect hash join（`perfect_hash_join_executor.cpp`）：
- 数组按 `build_range+1 = max-min+1` 分配（`:132`）；probe 在 `is_build_dense` 时走 fast-path：`result.Reference(lhs_output)` 并直接 `Dictionary(perfect_hash_table[i], build_sel_vec)`（`:268-290`），**稠密时不做逐行位测试、且引用而非拷贝**。
- 计划期用 `CanDoPerfectHashJoin(min,max)` + `MAX_BUILD_SIZE=1048576` + `PerfectHtThresholdSetting` 决策（`:65-140`）。

## 2. 数据观察（SF5 实测 CSV + TPC-H 基数）

TPC-H SF5 基数：region=5、nation=25、supplier=50K、customer=750K、part=1M、partsupp=4M、orders=7.5M、lineitem=30M。

`tpch_operator_timing.csv` 中 BHJ 实际生效（status=`yes`）的 join：

| Query | join | build(PK) 行数 | baseline | perfect | bitmap | 归类 |
|---|---|---|---|---|---|---|
| Q5 | `l_orderkey=o_orderkey`（build=`orders+…`，日期过滤→稀疏+宽） | 7.5M | 145ms | 151ms | **1548ms** | **模式1**（灾难性） |
| Q5 | `o_custkey=c_custkey`（build=customer，稠密） | 750K | 50ms | **30ms** | 94ms | **模式B**（BHJ 最慢） |
| Q5 | `c_nationkey=n_nationkey`（build=nation） | 25 | 3.6ms | 4.8ms | 4.8ms | 维度极小，无所谓 |
| Q9 | `l_orderkey=o_orderkey`（build=orders，稠密+窄 payload） | 7.5M | 1078ms | 1087ms | **113ms** | BHJ 大胜（对照） |
| Q9 | `ps_suppkey=s_suppkey`（build=supplier） | 50K | 127ms | 12ms | 12ms | BHJ/perfect 大胜 |
| Q10 | `l_orderkey=o_orderkey`（build=orders，稠密+窄 payload） | 7.5M | 227ms | 227ms | **143ms** | BHJ 胜（对照） |

### 2.1 关键反证：同结构 join 结果相反 → 根因是 payload 宽度，不是"密度"

- **Q9 vs Q5 的 `lineitem↔orders`**：build 都是 orders（7.5M）。Q9 该 join 的 RHS 仅为 `orders` 自身（窄），bitmap **113ms、比 baseline 快 10×**；Q5 该 join 的 RHS 是 `orders+customer+nation+region`（宽，含 o_/c_/n_/r_* 多列），bitmap **1548ms、比 baseline 慢 10×**。结构完全相同，唯一差异是 **RHS 输出列宽度**。
- **Q10 vs Q5 的同结构**：bitmap 分别为 **143ms vs 1548ms**（10× 差异），同样只因 Q5 在该 join 向上需要更多维度列（更宽 payload）。

→ BHJ 的 probe 代价由 **payload 工作集（行数 × 列宽）** 主导。原文档把 Q5 的 150MB 归因为"低密度"是因果倒错：150MB 来自 7.5M 行 × 宽列；稀疏只是让浪费更夸张。

### 2.2 两类模式的实测边界

- **模式1（稀疏）**：Q5 `l_orderkey=o_orderkey` 中 orders 被 `o_orderdate` 过滤，实际写入只占一部分 → `bitmap_size`(7.5M) ≫ 实际填充（~13–20%），payload 多数为空洞，probe（lineitem 30M）按 rowid gather 散布在 7.5M 宽区间 → L3 装不下 → cache miss。
- **模式B（稠密但慢）**：Q5 `orders↔customer` 中 customer 750K 基本全量，bitmap 100% 稠密。此时压缩**毫无收益**，BHJ 慢纯粹因为 (a) 无条件位测试 `:386`；(b) scatter 式 build 拷贝 vs perfect 的引用式输出。perfect 在稠密 fast-path 跳过位测试且引用输出，故 30ms < 94ms。

> 注意：Q9/Q10 的 `lineitem↔orders` 也是 orders 7.5M，但 orders 未被日期过滤（稠密）+ 窄 payload → 既非模式1 也非模式B，BHJ 大胜。这说明"是否优化"完全由**密度**与**payload 宽度**两个维度共同决定，二者独立。

## 3. 两类失效模式的重新界定（优化路线分治）

| 维度 | 模式1（低密度 / 稀疏 build） | 模式B（稠密但 BHJ 仍慢） |
|---|---|---|
| 触发条件 | `est_density = right.estimated_cardinality / pk->row_count` 低（如 < 0.3） | build 稠密（`popcount≈bitmap_size`），但键连续/可引用 |
| 浪费来源 | payload 按全维度行数分配，绝大部分是空洞；gather 散布 | 无条件逐行位测试；payload 整段拷贝 |
| 代表实测 | Q5 `lineitem↔orders` 1548ms | Q5 `orders↔customer` 94ms vs perfect 30ms |
| 初期手段 | `bitmapjoin=false` 回退 | 稠密 fast-path（跳过位测试）+ 与 perfect 对比 |
| 后期手段 | 轻量 hash 双重映射 + payload 顺序 append | payload 零拷贝引用（copy→reference） |
| 是否适用"压缩/回退"决策 | 是（方向1+方向2 都归这里） | 否（稠密无压缩空间，应优先 perfect 或 fast-path） |

**关键澄清（回应原文档方向1/方向2 的归并）**：原文档把"压缩(payload 按实际行数)"和"低密度回退"当作两个独立方向。实测表明二者**只在模式1 才有意义**：模式1 稀疏才有压缩空间、低密度才该回退；模式B 稠密既无压缩空间、回退也无收益（perfect 已能接管）。因此把方向1+方向2 合并为"模式1 专属路线"，模式B 走独立路线，是最干净的分治。

## 4. 优化路线 A：模式1（低密度 / 稀疏 build）

### 4.1 计划期低密度检测 → `est_density` 标识

在 `plan_comparison_join.cpp:107` 置位 `use_bitmap_join = true` **之前**，用已掌握的静态信息估计密度：

```cpp
// 伪代码（位于 `if (pk)` 内、置位 use_bitmap_join 之前）
idx_t bitmap_size = pk->row_count;
double est_density = (right.estimated_cardinality > 0)
                         ? double(right.estimated_cardinality) / double(bitmap_size)
                         : 1.0;
idx_t est_payload_bytes = EstimatePayloadBytes(join.rhs_output_columns.col_types, bitmap_size);

// 模式1 判定：低密度（且通常伴随宽 payload）
if (est_density < DENSITY_LOW_THRESHOLD) {     // 如 0.3
    hash_join.est_density = true;              // 标识：进入模式1 路线
    // 初期：直接回退（见 4.2）；后期：置 compact flag 走 4.3
}
```

- `pk->row_count`：来自 registry（`bitmap_join_meta`），即 bitmap 尺寸。
- `right.estimated_cardinality`：来自计划统计，反映上游谓词过滤后的**实际 build 行数**——低密度正是由此得来。
- `join.rhs_output_columns.col_types`：payload 列宽，用于估计工作集（`EstimatePayloadBytes`：定长用固定物理宽求和；VARCHAR 用保守常量如 32B 上界）。
- 不需要任何运行时测量，与 perfect hash join 的计划期 `CanDoPerfectHashJoin + PerfectHtThresholdSetting` 完全同构。

### 4.2 初期方案：`bitmapjoin=false` 回退到其它 join 形式

最简单、零 BHJ 运行时改动、风险最低：

```cpp
if (hash_join.est_density) {                   // 模式1：低密度
    hash_join.bhj_skip_reason = BitmapJoinSkipReason::LOW_DENSITY;
    pk = nullptr;                               // 不走 BHJ
    // 下方既有逻辑会自动选：普通哈希 join；若 CanDoPerfectHashJoin 适用则 perfect
}
```

- 直接消除 Q5 `lineitem↔orders` 的 1548ms 灾难点，回退到 baseline（145ms）附近。
- 复用已有 `bhj_skip_reason` 诊断（`:82` / `bitmap_join_meta.hpp:54-95`），在 EXPLAIN 暴露"为何没走 BHJ"，便于回归验证。
- 副作用：模式1 早期完全放弃 BHJ 的"按 rowid 完美成员判定"优势。但低密度+宽 payload 下 BHJ 本就劣势，回退是正确取舍。待 4.3 成熟后再把模式1 重新纳入 BHJ 体系。

> 可选增强：若同时 `est_payload_bytes > BitmapJoinMaxPayloadBytesSetting`（如 64MB），无论稠密与否都回退（宽 gather 必 cache miss）。这把"宽"维度（模式1 的宽 payload 情形）也兜住。

### 4.3 后期方案：轻量 hash 双重映射 + payload 顺序 append

目标：让模式1 重新享受 BHJ 的"按 rowid 完美成员判定"优势，同时消除全尺寸空洞 payload。

**核心思想——"双重映射"：**

- **映射①（membership，完美哈希成员判定）**：保留 bitmap。由 `rowid = key - offset` 直接 O(1) 判定是否在 build 内，**无哈希冲突、无探测分支**——这是 BHJ 相对普通哈希 join 的核心优势，必须保留（否则就退化成 4.2 的回退了）。
- **映射②（position，紧凑下标定位）**：用一个**轻量开放寻址哈希表**（容量 ≈ `popcount(bitmap)`，远小于 `bitmap_size`）把 `rowid → 顺序下标 seq`。build 时每遇到一个 build 行，**顺序 append** 到 `compact_payload[c][seq]`，并写 `hash[rowid] = seq`——**payload 无空洞、连续存放、可整体驻留 L3**。

**Probe 路径：** `rowid = key - offset` → 映射① 测试 membership（位测试，廉价）→ 命中则经映射② 取 `seq` → gather `compact_payload[seq]`。

**为何是"双重"而非"只用哈希"：** 若只用映射②（一个哈希表同时管 membership+position），就退化成普通哈希 join——30M 次 probe 要付出哈希计算 + 探测 + 比较，远慢于"bitmap 一位测试 + 哈希只取位置"。bitmap 负责最廉价的成员判定，哈希表只负责最少量的位置解析，二者分工最优，这就是"双重映射"的设计价值。

**为何用哈希而非前缀和 `dense_index`（对比原文档方向1）：**
- 原方向1 用 popcount 前缀和生成全尺寸 `dense_index[rowid]`（uint32，orders 7.5M×4B = 30MB）。
- 本方案用容量按 `popcount` 的轻量哈希（13% 密度下约 1M 项 × ~8B ≈ 8MB），**内存随实际数据量走、对超大维度更友好**，且复用普通哈希 join 已验证的开放寻址结构，更"轻量"。
- 二者等价地提供 position 映射；哈希版在 `bitmap_size` 极大时是更省的选择。实现时可二选一，建议优先哈希版。

**收益估计（Q5 `lineitem↔orders`）：** payload 工作集从 `7.5M × 宽列`（>150MB，溢出 L3）降到 `popcount × 宽列`（~1M × 宽列，约 20MB，可驻留 L3）；probe gather 目标地址连续，cache miss 大幅下降。预计从 1548ms 显著回落（目标低于回退 baseline 145ms）。

**实施要点：**
- 仅在 `est_density` 命中且 4.2 回退不充分时才启用（即"后期"阶段）。
- 压缩/重排放在 `FinalizeBitmap`（CombineBitmap 之后）一次性完成（O(popcount)），相对 30M 次 probe 的节省可忽略成本。
- `compact_payload` 与 `hash` 仅在模式1 后期分配；否则走原 `payload_columns[rowid]` 直取下标路径，不影响其它 join。

## 5. 优化路线 B：模式B（稠密但 BHJ 仍慢）

### 5.1 稠密 fast-path：跳过逐行位测试

现状：BHJ 没有"build 已全稠密"的概念（perfect 有 `is_build_dense`），所以即便 bitmap 100% 置位，`:386` 仍为每行付出一次位测试 + 分支。对 30M 行 lineitem probe，这是千万级无效分支，是模式B 中 BHJ 慢于 perfect 的直接原因。

改造：在 `CombineBitmap` 后若 `popcount(global_bitmap) == bitmap_size`，置 `is_build_dense = true`；`ProbeBitmap` 在 `is_build_dense` 时跳过 `:386` 的位测试与分支，直接 gather `payload[rowid]`。

```cpp
// FinalizeBitmap 之后
is_build_dense = (popcount(global_bitmap) == bitmap_size);

// ProbeBitmap 内
if (!is_build_dense) {
    if (!bitmap.RowIsValidUnsafe(rowid)) continue;   // 原 :386
}
// 命中（或稠密）后 gather payload[rowid]
```

### 5.2 与 perfect hash join 对比（关键边界）

必须明确：即便加了 5.1 的 fast-path，BHJ 稠密路径**仍比 perfect 多一笔开销**——

- **perfect 稠密 fast-path**（`:268-290`）：`result.Reference(lhs_output)` + `Dictionary(perfect_hash_table[i], build_sel_vec)`，**引用式输出、零拷贝、且按 build_sel 顺序产出**。
- **BHJ 稠密 fast-path**（5.1）：仍用 `Slice(*payload_columns[rowid], build_sel_vec)` 做 **gather 拷贝**，且 gather 目标是 `payload[rowid]` 的**随机地址**（除非 payload 连续）。

→ 当 payload 小到可驻留 L3，gather 廉价，BHJ fast-path 接近 perfect；当 payload 宽（如 customer 多列），gather 仍有 miss 风险。因此对比结论是：
- **键连续且稠密时，优先 perfect**（数组尺寸相同、locality 相同、且无位测试、且引用零拷贝）——5.1 的 fast-path 在此只是"让 BHJ 不至于太难看"的兜底。
- **fast-path 真正有价值的场景**：键**不连续**（`CanDoPerfectHashJoin` 不适用，perfect 无法建），但 bitmap 却**恰好全稠密**（范围内键全部出现）。此时 perfect 不可用，BHJ 稠密 fast-path 成为最优解。计划期用 `CanDoPerfectHashJoin` 区分这两类：适用 perfect 就交给 perfect；不适用但稠密就走 BHJ + fast-path。

### 5.3 payload 复制优化（像模式1 一样思考"能否不拷贝"）

现状：BHJ build 总是把 RHS 输出列 **scatter 拷贝** 到 `payload_columns[rowid]`（`:280-301`），是一份全尺寸拷贝。模式1 用"顺序 append 仅拷贝存在行"解决了稀疏浪费；模式B 稠密无空洞，但仍有**不必要的整段拷贝**可优化。

**类比模式1 的思路——能引用就不拷贝：**
- perfect 稠密 fast-path 直接 `Reference(lhs_output)`，**零拷贝**。BHJ 应采纳同样策略：当 build 的 RHS 输出列**直接可由 rowid 寻址到原始 build vector**（即这些列来自单一连续源、无投影/重排）时，probe 直接 `Reference`/`Dictionary` 原始列，而不是 gather 已拷贝的 `payload_columns`。
- 适用条件：RHS 输出列是"干净维度列"（如 customer 维度自身几列），其原始 Vector 已按 rowid 连续存放 → 可直接引用，省掉 5.2 中提到的 gather 随机访问与 build 期整段拷贝。
- 不适用条件：RHS 输出列来自**多表 join 结果**（如 Q5 的 `orders+customer+nation+region`），无法整体引用，仍需拷贝到 `payload_columns`。这类宽/多源 payload 正是模式B 中 BHJ 仍慢的部分，应优先交给 perfect 或 5.1 fast-path，并在计划期用 `est_payload_bytes` 兜底回退（见 4.2 增强）。

**收益：** 对"单源稠密维度"（如 customer 750K）类 join，BHJ 可做到与 perfect 同级的零拷贝引用输出，把 `orders↔customer` 的 94ms 拉近 perfect 的 30ms，且无需 perfect 的"键连续"前提。

---

## 6. 度量与验证建议

1. **payload 工作集可观测化**：在 `BitmapJoinExecutor` 构造期记录 `bitmap_size × Σ列宽` 与 `popcount` 到 profiler，EXPLAIN ANALYZE 直接看每个 BHJ 节点的 payload MB、密度、probe cache miss（`perf stat -e cache-misses`）。
2. **A/B 回归（分阶段）：**
   - **阶段0（仅加计划期护栏）**：模式1 回退（4.2）+ 稠密优先 perfect（5.2）。预期 Q5 整体回到 baseline 附近（消除 1548ms 灾难点），Q9/Q10 不受影响（稠密窄 payload 仍走 BHJ）。
   - **阶段1（模式1 后期）**：启用 4.3 双重映射 + 顺序 append。重点验证 Q5 `lineitem↔orders` 能否从回退后的 baseline（145ms）进一步下降。
   - **阶段2（模式B 后期）**：启用 5.1 fast-path + 5.3 零拷贝。对比 `orders↔customer` 在"BHJ fast-path+引用" vs "perfect" 下的耗时。
3. **密度估计校准**：打印 `right.estimated_cardinality / pk->row_count`（计划期）与真实 `popcount(bitmap)/bitmap_size`（运行时），确认一致，避免护栏误判（估计密度高但实际稀疏 → 漏判模式1）。
4. **阈值调参**：扫描 `DENSITY_LOW_THRESHOLD`（0.2/0.3/0.5）与 `BitmapJoinMaxPayloadBytesSetting`（16/32/64/128MB）下的 Q5/Q9/Q10 总耗时，取拐点。

## 7. 风险与边界

- **估计偏差**：`estimated_cardinality` 在谓词选择性估计不准时可能失真，导致模式1 误判。用 `bhj_skip_reason` + EXPLAIN 持续监控；必要时退化为"默认仍走 BHJ，仅对超大/超宽维度硬性回退"。
- **模式1 后期哈希表的探测成本**：开放寻址哈希在 probe 端仍有哈希计算 + 比较，需 A/B 确认"bitmap 成员判定 + 轻量哈希取位置"净收益 > "直接 `payload_columns[rowid]` 直取"（后者无哈希但需全尺寸 payload 驻留）。稀疏度越低（popcount 越小），哈希表越小越划算。
- **5.3 零拷贝的引用安全**：`Reference` 原始 build 列要求 build 列生命周期覆盖 probe，且不被后续算子改写；需确认 BHJ 的 build 侧 Vector 在 probe 期仍有效（通常成立，但多源 join 的物化列要小心）。
- **列宽估计保守性**：VARCHAR 用常量估计可能高估 payload，导致本可 BHJ 的 join 被误回退；可后续按实际平均长度细化。
- **与 perfect hash join 的分工**：perfect 仅限 INNER 单等值 + 键连续（`build_range+1 ≤ MAX_BUILD_SIZE`）。BHJ 路线 A/B 需确保：模式1 后期双重映射不依赖键连续；模式B fast-path 仅在 perfect 不适用时才成为主路径。
- **不改变正确性**：所有改动仅影响"是否走 BHJ / 是否压缩 / 是否位测试 / 是否拷贝"，不改变 join 语义；回退路径即现有普通哈希 join 与 perfect，已被大量测试覆盖。

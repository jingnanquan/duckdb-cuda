## 2. 名词与缩略语

| 术语 | 含义 |
| ---- | ---- |
| HJ | HashJoin（DuckDB 默认等值连接算子，`PhysicalHashJoin`） |
| PHJ | PerfectHashJoin（DuckDB 现有的稠密整型小范围 build 优化路径，`PerfectHashJoinExecutor`） |
| BHJ | **Bitmap HashJoin**（本项目新增算子，下文核心） |
| rowid | 主表新增的、从 0 起递增的稠密自增列（`UBIGINT`） |
| `*_ref` | 外键表新增的列：把原本指向主键值的字段替换为指向主表 `rowid` 的稠密整数 |
| Build 侧 | HashJoin 中维护 hash 表的一侧（一般是较小、含主键的表） |
| Probe 侧 | HashJoin 中遍历查询 hash 表的一侧 |
| Bitmap | 长度为 `build_table.row_count()` 的位图，第 `i` 位为 1 表示主表第 `i` 行通过了 build 侧 filter |
| 主外键等值连接 | build 侧 join key 在表内**唯一**（不要求 PK，UNIQUE 即可）的等值 inner/semi join |
| `DataChunk` | DuckDB 列式批数据，最大 `STANDARD_VECTOR_SIZE`（默认 2048）行 |
| `ValidityMask` | DuckDB 现有 64-bit word bitmap 实现，用于 NULL 标记，本项目**复用**作为 join bitmap |
| Pipeline / MetaPipeline | DuckDB push-based 执行单元 |

## 3. 需求与目标

### 3.1 业务需求

在 DuckDB 现有 SQL/optimizer/执行框架下，对 TPC-H `parquet` 多 HashJoin 查询提供新的 **Bitmap HashJoin** 算子，覆盖：

1. **多 hashjoin、主外键 inner-join 链** 的查询（典型如 TPC-H Q5/Q9/Q10），用 bitmap 替代 hash 表。
2. **build 侧 join key 唯一**、外键侧**取值稠密**（已被预处理为 `*_ref`）的等值 inner / semi / right-semi join。

> 与 DuckDB 自带 `PerfectHashJoinExecutor` 的关键差别：PHJ 要求 build 侧 key 是**整数**且 max-min 在静态阈值内（默认 1M），而 BHJ 通过**预处理**强制把所有主外键映射成稠密 rowid，使得**任意业务主键类型**（字符串、复合主键、超出 1M 阈值的整型）都可走 bitmap 路径，并且 build 阶段无需回表 hash 表。

### 3.2 功能性需求

- F1：新增 `bitmap_join` catalog 属性：标记表的某列对（PK 列、PK rowid、FK 表的 `*_ref` 列）的预绑定关系。
- F2：新增表预处理脚本 `b_idea/scripts/add_bitmap_columns.py`，对符合条件的 TPC-H parquet 表追加 `rowid` / `*_ref` 列。
- F3：新增 `BitmapJoinExecutor`（参考 `PerfectHashJoinExecutor` 风格，但内部不依赖 `JoinHashTable`）。
- F4：在 `PhysicalHashJoin` 中新增 `use_bitmap_join` 开关，与 `use_perfect_hash` 互斥，优先级高于 PHJ。
- F5：新增查询计划注入脚本 `b_idea/scripts/inject_bitmap_plan.py`，在不改 binder/optimizer 的前提下手工把指定 join 节点改写为 BHJ。
- F6：BHJ 在异常 / 不满足条件 / 列缺失时**自动回退** 到原 `PhysicalHashJoin`（保留 build hashtable 路径），对外语义不变。

### 3.3 非功能性需求

- N1：CPU 默认路径不退化；关闭 `use_bitmap_join` 时整条调用链等价于原 DuckDB。
- N2：BHJ 算子单元测试覆盖率 ≥ 70%；correctness 测试在 SF1/SF10 上 Q5/Q9/Q10 与原 DuckDB 结果**逐行 bit-exact** 一致。
- N3：表预处理一次性、增量友好（只追加列，不破坏原 parquet schema）。
- N4：Bitmap 内存占用 = `build_row_count / 8` 字节，需保证 SF10（最大表 lineitem 60M 行 ≈ 7.5MB / customer 1.5M 行 ≈ 188KB）下完全在 L2/L3 cache 友好范围内。

### 3.4 非目标（Out of Scope）

- 不重写 parser / binder。
- 不实现非等值、外连接、ANTI、MARK 等复杂 join 类型的 bitmap 化（保留 fallback）。
- 不在 build 侧 join key **不唯一**时尝试 bitmap（这种语义需要 1→N 映射，超出本期范围）。
- 不实现跨 query 的 bitmap cache。
- 不改造 DuckDB 原生表（仅作用于已预处理的 parquet 外部表）。

### 3.5 MVP 与里程碑

| 里程碑 | 范围 | 目标 |
| ------ | ---- | ---- |
| M0 | Q5/Q9/Q10 在原 DuckDB 上的基线性能数据 + perf 火焰图 | 量化 HashJoin 占比，确认改造收益空间 |
| M1 | 表预处理脚本 + catalog 元数据 | parquet 表追加 `rowid` / `*_ref` 列；`PRAGMA bitmap_join_meta` 可查 |
| M2 | `BitmapJoinExecutor` MVP（仅支持 inner join、单等值条件、build 侧 unique） | 单 join 端到端跑通，结果与 HJ 一致 |
| M3 | 查询计划注入脚本 + 在 Q5/Q9/Q10 上替换 1 个 join 节点 | 单点性能对比 |
| M4 | 多 join 节点全量替换 + 端到端 Q5/Q9/Q10 | SF10 端到端加速 ≥ 30% |
| M5 | optimizer rule 自动选择 BHJ | 关闭注入脚本，自动化 |

## 4. 现状分析：DuckDB 现有 HashJoin / PerfectHashJoin 路径

> 本节是后续模块设计的基线，所有改动位置都引用本节标识的代码点。

### 4.1 PhysicalHashJoin 端到端调用链

入口：[physical_hash_join.cpp](/data/workspace/database/duckdb-cuda/src/execution/operator/join/physical_hash_join.cpp)

```text
[Build 侧 pipeline]
  PhysicalHashJoin::GetGlobalSinkState   (line 309)
    new HashJoinGlobalSinkState                       // 含 hash_table, perfect_join_executor, use_perfect_hash
  PhysicalHashJoin::Sink                 (line 329)   // 每个 build chunk → ht.Build
  PhysicalHashJoin::Combine              (line 357)   // 合并 local hashtable
  PhysicalHashJoin::PrepareFinalize      (line 447)
  PhysicalHashJoin::Finalize             (≈ line 600+) // 触发 HashJoinFinalizeEvent / HashJoinTableInitEvent

[Probe 侧 pipeline]
  PhysicalHashJoin::GetOperatorState     (header line 62)
  PhysicalHashJoin::ExecuteInternal      (header line 70)
    if (sink.perfect_join_executor && sink.use_perfect_hash)
      → PerfectHashJoinExecutor::ProbePerfectHashTable      // 走稠密整型路径
    else
      → ht.Probe(...) + ScanStructure::Next                 // 走通用 hashtable 路径

[Right-semi/anti 输出]
  PhysicalHashJoin::GetDataInternal      (header line 77)
```

关键观察（用于差距分析）：

1. **Build 阶段**：`Sink` 把每个线程的 chunk 写入 thread-local `JoinHashTable`，`Combine` 串行把它们 push 进 global，`Finalize` 在 `HashJoinFinalizeEvent` 中并行做 partition + pointer table 写入。此阶段存在串行的合并 + 最后等待全部完成才能进 probe。BHJ 把这一阶段替换为「按 build 侧 rowid 直接 set bit」，**无 partition、无 pointer table**。
2. **Probe 阶段**：通用路径里 `ht.Probe` 要做 hash 计算 + chain 遍历 + key 比较 + 回表 gather。BHJ 把这一阶段替换为「读 `*_ref` 列 → bitmap[ref] → 二元判断」，无 hash、无比较、无 chain。
3. **Build/Probe pipeline 依赖**：[physical_join.cpp](/data/workspace/database/duckdb-cuda/src/execution/operator/join/physical_join.cpp) `PhysicalJoin::BuildJoinPipelines` 把 build 侧作为 child meta-pipeline，并 `current.AddDependency(child_meta_pipeline.GetBasePipeline())`。**这条依赖 BHJ 必须保留**——bitmap 同样需要等 build 侧 scan 完成，但 build 工作量极小（只 set bit）。

### 4.2 PerfectHashJoinExecutor 路径剖析

入口：[perfect_hash_join_executor.cpp](/data/workspace/database/duckdb-cuda/src/execution/operator/join/perfect_hash_join_executor.cpp)

PHJ 关键约束（来自 `CanDoPerfectHashJoin` line 67~115）：

1. 只支持 inner join + 单等值条件。
2. join key 必须是**整数**（`TypeIsInteger`）。
3. build 侧没有 nested 类型。
4. `[min, max]` 范围 ≤ `MAX_BUILD_SIZE = 1048576`。
5. `ht.Count() <= build_range`（无重复键）。

**性能瓶颈**（与初步设计「现有 PHJ 性能差」的诊断对齐）：

1. **PHJ 仍然依赖完整的 `JoinHashTable`**（成员 `JoinHashTable &ht;`）：必须先走完 `Sink → Combine → Finalize` 才能调用 `BuildPerfectHashTable` → `FullScanHashTable`（line 148~191）。也就是说，**PHJ 是「在 hashtable 之上再加一层 dictionary 优化」**，省掉的是 probe 侧的 chain 遍历，并没有省掉 build 侧的 hashtable 构建。
2. `FullScanHashTable` 中 `data_collection.Gather` 用 `tuples_addresses` 回表（line 174），仍然是一次随机访问。
3. `bitmap_build_idx` 是 `ValidityMask`，其用途仅为「duplicate 检查 + null 占位」，并非真正的 join bitmap。
4. `CanDoPerfectHashJoin` 在每次 chunk 都可能被调用（与初步设计「多次 CanDoPerfectHashJoin 判断」一致）。

**结论：PHJ 节省了 probe 侧的 hash + chain，但没有省掉 build 侧的 hashtable，且对 key 类型/范围严苛。BHJ 的目标是同时省掉 build 与 probe 两侧的 hash 操作。**

### 4.3 DuckDB 列式数据结构对 BHJ 友好的点

| 现有能力 | BHJ 复用方式 |
| -------- | ------------ |
| `ValidityMask`（64-bit word bitmap，`Set/Reset/RowIsValid`） | 直接作为 build bitmap 的存储 |
| `UnifiedVectorFormat` + `SelectionVector` | probe 阶段读 `*_ref` 列、产出 sel_vec |
| `DictionaryVector::CreateReusableDictionary` | 主表全列回表时可作为字典向量 |
| `TupleDataCollection::Gather` | 主表 RHS 输出列的回表（与 PHJ 复用一致） |
| `DataChunk::Slice` | probe 输出按 sel_vec 过滤 |

## 6. 核心模块详细设计

### 6.1 模块 M-S：表预处理脚本（add_bitmap_columns.py）

#### 6.1.1 模块职责

将 TPC-H parquet 原表升级为 BHJ 友好版本：

1. 对每张主表 `T`，若 PK 已是稠密 0 起递增的 `BIGINT`，跳过 rowid 追加；否则追加 `__rowid` 列，类型 `UBIGINT`，从 0 起。
2. 对每张外键表 `F`，对每个外键列 `fk_col` 引用 `T.pk_col`，追加 `fk_col__ref` 列：值 = `T` 中 `pk_col == fk_value` 的行的 `__rowid`（NULL 对应 NULL）。
3. 输出 `bitmap_join_meta.json`，记录所有「(F.fk_col__ref) → (T.__rowid)」绑定关系，供 catalog 加载。

#### 6.1.2 输入 / 输出 / 数据结构

```json
// bitmap_join_meta.json 示例
{
  "version": 1,
  "bindings": [
    {
      "pk_table":  "customer",
      "pk_column": "c_custkey",
      "rowid_column": "c_custkey",            // TPC-H 中 c_custkey 已稠密，复用
      "row_count":  1500000
    },
    {
      "fk_table":   "orders",
      "fk_column":  "o_custkey",
      "ref_column": "o_custkey__ref",         // 新增列
      "pk_table":   "customer",
      "pk_column":  "c_custkey"
    }
  ]
}
```

#### 6.1.3 关键流程

```text
for each (pk_table, pk_col, fk_table, fk_col) in tpch_constraints.csv:
    # 1) 读 pk 表，构造 dict: pk_value -> rowid
    pk_df = read_parquet(pk_table.parquet)
    if is_dense_zero_based_int(pk_df[pk_col]):
        rowid_col = pk_col
    else:
        pk_df["__rowid"] = arange(len(pk_df))
        rowid_col = "__rowid"
        write_parquet(pk_table.parquet, pk_df)
    pk_map = dict(zip(pk_df[pk_col], pk_df[rowid_col]))

    # 2) 读 fk 表，按 pk_map 生成 ref 列
    fk_df = read_parquet(fk_table.parquet)
    ref_col_name = f"{fk_col}__ref"
    fk_df[ref_col_name] = fk_df[fk_col].map(pk_map)   # 缺失为 NULL
    write_parquet(fk_table.parquet, fk_df)

    # 3) 写 meta
    meta.bindings.append({...})

write_json(bitmap_join_meta.json, meta)
```

#### 6.1.4 多方案对比

| 方案 | 描述 | 取舍 |
| ---- | ---- | ---- |
| A. 原地修改 parquet | 直接覆盖原文件 | 简单，但破坏原 benchmark 表 |

### 6.4 模块 M-E：BitmapJoinExecutor（核心）

#### 6.4.1 模块职责

实现 build/probe 两阶段的 bitmap join，**完全不依赖 `JoinHashTable`**，与 PHJ 形成对比：

| 阶段 | PHJ | **BHJ** |
| ---- | --- | ------- |
| build 入数据 | `ht.Build`（写 row layout + hash） | `bitmap.set(rowid)`（位运算） |
| build finalize | `ht.Finalize`（partition + pointer table） | 无（thread-local bitmap OR 合并） |
| probe 计算 hash | 是 | **否** |
| probe 比较 key | 是（`PerfectHashJoinExecutor` 比 min/max + bitmap） | **否，仅 1 次位测试** |
| 回表 build payload | `Gather`（指针随机访问） | 用 rowid 作为 dictionary index 直接 slice |

#### 6.4.2 数据结构

```cpp
// src/include/duckdb/execution/operator/join/bitmap_hash_join_executor.hpp
namespace duckdb {

class PhysicalHashJoin;

struct BitmapJoinResolved {
    const BitmapJoinPKBinding *pk = nullptr;   // build 侧
    const BitmapJoinFKBinding *fk = nullptr;   // probe 侧
};

//! 全局/局部共享：build 阶段构建出的 bitmap + 主表 RHS 输出列的物化缓存
struct BitmapJoinBuildState {
    //! 长度 = pk->row_count，对齐到 64 bit；表示 build 侧通过 filter 的 rowid 集合
    ValidityMask bitmap;
    idx_t        bitmap_size = 0;

    //! 主表 RHS 输出列的稠密物化（按 build 侧 scan 顺序追加），
    //! 索引 = build 侧 rowid（外面 probe 时用 ref 直接索引）。
    //! - 如果 RHS 的 join 输入就是「整张主表」，则 scan 时直接顺序填满；
    //! - 否则按 rowid scatter 写入对应位置（写一次，读 N 次）。
    vector<unique_ptr<Vector>> rhs_payload_columns; // 大小 = bitmap_size
    bool rhs_payload_dense = false;                 // true 表示与 rowid 完全对齐
};

class BitmapJoinExecutor {
public:
    explicit BitmapJoinExecutor(const PhysicalHashJoin &join);

    // ---------- Build ----------
    // 单线程版本（M2 MVP）；多线程见 §7.2。
    void SinkBitmap(ExecutionContext &ctx, DataChunk &chunk);
    void CombineBitmap(BitmapJoinExecutor &other);   // OR 合并 thread-local
    void FinalizeBitmap();                            // no-op / 标记 ready

    // ---------- Probe ----------
    unique_ptr<OperatorState> GetOperatorState(ExecutionContext &ctx);
    OperatorResultType ProbeBitmap(ExecutionContext &ctx,
                                   DataChunk &input,
                                   DataChunk &lhs_output_columns,
                                   DataChunk &result,
                                   OperatorState &state);

    // ---------- 诊断 ----------
    bool   IsReady() const { return ready_.load(); }
    idx_t  BitmapSize() const { return build_state_.bitmap_size; }

private:
    const PhysicalHashJoin &join_;
    BitmapJoinBuildState   build_state_;
    std::atomic<bool>      ready_ {false};
};

class BitmapJoinOperatorState : public OperatorState {
public:
    BitmapJoinOperatorState(ClientContext &ctx, const PhysicalHashJoin &join);

    SelectionVector probe_sel_vec; // 命中的 probe 行号
    SelectionVector build_sel_vec; // 命中行对应的 build rowid
    DataChunk       join_keys;     // 已抽出的 ref 列
    ExpressionExecutor probe_executor; // 复用 PHJ 风格
};

} // namespace duckdb
```

#### 6.4.3 接口语义

| 方法 | 输入 | 输出 / 副作用 | 复杂度 |
| ---- | ---- | -------------- | ------ |
| `SinkBitmap(chunk)` | build 侧 chunk，包含 rowid 列（`bitmap_build_rowid_idx`） | 对每个 valid 行：`bitmap.SetValid(rowid)`；同时把 RHS 输出列按 rowid scatter 到 `rhs_payload_columns` | O(rows)，纯位运算 + 顺序写 |
| `CombineBitmap(other)` | 另一个 thread-local executor | bitmap 按 64-bit word OR；payload 按 rowid 不冲突 merge | O(bitmap_size / 64) |
| `FinalizeBitmap()` | — | `ready_ = true` | O(1) |
| `ProbeBitmap(input, lhs_out, result, state)` | probe chunk（含 ref 列），LHS 输出列 chunk | 产出 join 结果 chunk | O(rows) |

#### 6.4.4 关键流程：Build

```text
for each thread t:
    local_bitmap[t] = ValidityMask(bitmap_size, all_invalid)

  Sink(chunk):
      ref_vec = chunk.data[bitmap_build_rowid_idx]    // build 侧的 rowid 列
      for i in 0..chunk.size():
          if !valid(ref_vec, i): continue
          rowid = ref_vec[i]
          local_bitmap[t].SetValidUnsafe(rowid)
          # RHS payload：把 chunk 的 rhs 输出列按 rowid scatter 到 build_state_.rhs_payload_columns

Combine:
    global_bitmap |= local_bitmap[t]            // 64-bit word OR
    payload merge：每个 rowid 只可能被一个线程写入（build 侧 unique），无冲突

Finalize:
    ready_ = true，触发下游 probe pipeline 解除依赖
```

> 与 PHJ 相比，**没有** `data_collection.Gather`、**没有** `pointer table`，无 partitioning。

#### 6.4.5 关键流程：Probe

```text
ProbeBitmap(input, lhs_out, result):
    state.join_keys.Reset()
    state.probe_executor.Execute(input, state.join_keys)   // 产生 ref vec
    ref_vec = state.join_keys.data[0]
    UnifiedVectorFormat fmt; ref_vec.ToUnifiedFormat(count, fmt)

    sel_idx = 0
    for i in 0..count:
        if !fmt.validity.RowIsValid(i): continue
        rowid = fmt.data[fmt.sel->get_index(i)]
        if rowid >= bitmap_size: continue          // 防御性
        if global_bitmap.RowIsValidUnsafe(rowid):
            probe_sel_vec[sel_idx] = i
            build_sel_vec[sel_idx] = rowid
            sel_idx++

    if sel_idx == count and inner_join:
        result.Reference(lhs_out)
    else:
        result.Slice(lhs_out, probe_sel_vec, sel_idx, 0)

    for j in 0..join.rhs_output_columns.size():
        // 用 rowid 当 dict index，直接 dictionary 引用
        result.data[lhs_count + j].Dictionary(
            build_state_.rhs_payload_columns[j], build_sel_vec)

    return NEED_MORE_INPUT
```

> 关键性能特性：probe 是**完全分支预测友好**的「读 ref → 一次位测试 → 写入 sel_vec」，无 hash、无比较、无随机访问 hash table。

#### 6.4.6 多方案对比

| 方案 | 描述 | 取舍 |
| ---- | ---- | ---- |
| A. 直接复用 `JoinHashTable`，仅 build 端额外维护 bitmap | 改动小 | 仍然付出 hashtable 全部代价，背离初步设计 |
| **B. 独立 BHJ executor，bitmap + payload 列**（选用） | 与 PHJ 风格一致，零 hashtable | build/probe 双侧均提速；payload 物化是新增内存开销，但 SF10 完全可控 |
| C. 仅 bitmap，不缓存 payload，回表时 ParquetReader 二次读 | 最省内存 | 二次 IO，得不偿失 |

## 7. 关键算法与数据流

### 7.1 Build 端 bitmap 构建并行化

```text
全局：
  global_bitmap   = ValidityMask(N, all_invalid)
  payload_cols[k] = Vector(N) for each rhs output col
线程 t：
  Sink(chunk):  for each row, set local_bitmap word atomically OR (or thread-local + Combine)
Combine：global_bitmap |= local_bitmap[t]
Finalize：ready_=true → 触发 probe pipeline 解除依赖（保留 BuildJoinPipelines 的 dependency）
```

实现层面有两种并发方案：

| 方案 | 描述 | 取舍 |
| ---- | ---- | ---- |
| **B1（选用）** | thread-local bitmap + Combine OR | 与 DuckDB 现有 sink/combine 模型对齐；零原子开销 |
| B2 | 全局 atomic-OR 直接 set bit | bitmap 较小时 cache line 竞争严重 |

### 7.2 Build 端 RHS payload 物化

- 当 build 侧的输入恰好是「主表全表 scan + filter + projection」（TPC-H Q5/Q9/Q10 常态），rowid 与 build chunk 的物理顺序**不一定对齐**（可能因为 pushdown filter 而稀疏）。但 rowid 唯一，按 rowid scatter 写入 `payload_cols[k][rowid]` 永远是无冲突的。
- 当 build 侧通过 join key 是 PK 的 join 链顶端（即 build 输入仍是 PK 表），payload scatter 的 cache locality 取决于 rowid 是否单调；M2 MVP 不做特殊优化，M4 阶段评估是否需要 reorder。

### 7.3 Probe 端的零比较路径

```cpp
inline bool ProbeOne(uint64_t *bitmap_words, uint64_t rowid) {
    // ValidityMask 内部即是 64-bit word；与之等价
    return (bitmap_words[rowid >> 6] >> (rowid & 63)) & 1u;
}
```

向量化版本（处理 STANDARD_VECTOR_SIZE 行）使用 SIMD gather + 位测试，预期 < 1ns/行。

### 7.4 与现有 PHJ probe 的等价语义证明

- 输入：probe chunk 的 ref 列（NULL 行被 `validity` 过滤）。
- ref = rowid in [0, N)（脚本生成阶段保证），**等价于** PHJ 中 `min_value=0, max_value=N-1` 的整数键。
- bitmap.RowIsValid(rowid) 等价于 PHJ 的 `bitmap_build_idx.RowIsValid(idx)`（PHJ 中已用同一 ValidityMask 类型表达）。
- payload 用 `result.data[k].Dictionary(payload_cols[k], build_sel_vec)` 等价于 PHJ 的 `result_vector.Dictionary(perfect_hash_table[k], state.build_sel_vec)`。

## 9. 资源管理

### 9.1 内存

| 数据 | 大小估算 | 生命周期 |
| ---- | -------- | -------- |
| global_bitmap | `ceil(N / 64) * 8` 字节 | build sink ~ probe 结束 |
| 每线程 local_bitmap | 同上 / 线程 | sink 期间 |
| payload_cols[k] | `N * sizeof(col_k)` （内含 validity） | build sink ~ probe 结束 |

> 最大场景 lineitem 60M 行：bitmap 7.5 MB，5 个 RHS 列（按 8B 估算）共 2.4 GB。BHJ 在 build 侧表为 lineitem 的场景**不应**被选中（lineitem 的 join key 不唯一），由 §6.6 rule 自动排除。Q5/Q9/Q10 中 build 侧最大是 customer/orders（≤ 15M 行），payload 内存可控。

### 9.2 与 BufferManager 的协作

- payload_cols 的 backing buffer 通过 `BufferAllocator::Get(context)` 申请，参与内存预算（与 PHJ 一致）。
- 当 build 侧行数超过阈值 `bitmap_join_max_build_rows`（默认 64M）时，BHJ rule 不选中，回退 HJ。

### 9.3 错误恢复

- 任何 build 阶段异常（如 ref 超界）→ 抛 `InternalException`，由 `Executor::WorkOnTasks` 捕获并设置 query error；不会污染 bitmap（局部变量）。
- M2 MVP 阶段：失败不自动回退，仅给出明确报错；M4 引入「per-join fallback」（见 §11）。

## 11. 错误处理、回退与降级

### 11.1 静态校验（计划期）

- catalog 中无对应 PK/FK 绑定 → 不选中 BHJ。
- join_type 不在 {INNER, RIGHT_SEMI} → 不选中。
- 等值条件多于 1 个 → 不选中（M5 后可扩展为多 ref 列联合，本期 OOS）。

### 11.2 运行期降级

| 触发条件 | 处理 |
| -------- | ---- |
| sink 阶段发现 build 侧 rowid 列存在 NULL 但 PK 标称非空 | M2：抛错；M4：清除标记，整 join fallback HJ |
| ref 值越界（`>= bitmap_size`） | M2：抛错；M4：跳过该行（视为不匹配） |
| 内存超限 | sink 早期检测，立即 fallback HJ（恢复 hash_table 路径） |

### 11.3 fallback 实现策略

为 M4 准备：在 `HashJoinGlobalSinkState` 中保留 `hash_table` 的延迟构造能力。当 BHJ 决定 fallback 时，重放 build 侧 chunk（来自缓存的 `local_chunks`）到 `JoinHashTable`。**M2 阶段先不做缓存**（避免内存翻倍），改为直接报错并要求用户关闭 BHJ。

## 12. 性能目标与评估方案

### 12.1 基线（M0 必产出）

| Query | DuckDB default (HJ + PHJ on) | DuckDB (PHJ off) | hashjoin 占比 |
| ----- | ---------------------------- | ---------------- | ------------- |

| Q9 | T_q9_a | T_q9_b | p_q9 |

> M0 阶段实测后填入；perf 火焰图保存于 `b_idea/perf/<sf>/<query>.svg`。

### 12.2 BHJ 目标（端到端）

| 阶段 | Q5 / Q9 / Q10 SF10 加速比目标 |
| ---- | ----------------------------- |
| M2 单 join 替换 | 该 join 节点 build+probe 总时间 ≥ 2× |
| M4 全 join 替换 | 端到端 latency ≥ 30% 提升 |
| M5 自动 rule | 自动选中率 ≥ 90%（在含 PK/FK 绑定的 join 上） |

### 12.3 微基准

`benchmark/micro/bitmap_join/*.benchmark`：

- 单 join，build_size ∈ {10K, 100K, 1M, 10M}，probe_size = 10×build；
- 对比维度：HJ default、PHJ、BHJ；
- 指标：build/probe 各自吞吐（rows/s）、L1/L2 miss、IPC。

### 12.4 失败判据

- 任一 query 在 BHJ 路径下结果与基线不一致 → 阻塞性 bug；
- BHJ 端到端反而劣化 → 触发 §16 风险 R-PERF。

## 16. 风险登记表

| ID | 风险 | 等级 | 缓解 |
| -- | ---- | ---- | ---- |
| R-DATA | parquet 表预处理破坏原 schema | 中 | 输出到独立目录，原文件保留；脚本幂等 |
| R-MEM | RHS payload 物化导致内存翻倍 | 中 | §9.1 阈值 + rule 不选中大 build；M4 引入按需物化 |
| R-PERF | bitmap miss 比例高时反而比 HJ 慢（bitmap 太大且稀疏，cache miss） | 中 | 微基准评估；rule 在 build_size > 阈值时不选中 |
| R-CORR | rowid / ref 列与原表关系错误 | 高 | 预处理脚本附带断言 + sqllogic correctness 守门 |
| R-CONC | 多线程 sink 时 payload scatter 出现并发写同一 rowid | 高 | build 侧 unique 由 catalog 强制；脚本预处理时去重检查 |
| R-INTEG | 与 PHJ / 现有 hashtable 路径互斥不彻底 | 中 | §6.3 三路并列分支 + 单元测试覆盖 |
| R-OPT | M5 自动 rule 误选 BHJ | 中 | 仅在 catalog 明确绑定时启用；保留全局 PRAGMA off |

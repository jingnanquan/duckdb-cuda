# 进展汇报：基于 Bitmap 的 HashJoin 加速优化（DuckDB / TPC-H）

## 一、背景与动机

TPC-H 是业界标准的分析型（OLAP）查询基准，其中多张表之间的多路 **HashJoin**（等值连接）是较为耗时的算子之一。我们在对 TPC-H 典型查询（Q5、Q9、Q10 等）做性能剖析时发现：

- 这些查询普遍包含 3~5 个 HashJoin，多数是**维度表（主键）与事实表（外键）**之间的等值连接（例如 `customer ⋈ orders`、`orders ⋈ lineitem`）；
- HashJoin 算子在整体查询耗时中占比很高，Q5:29.7、Q9:67.8%、Q10:31%。（parquet格式下占比会下降，Q9降为46.7%）；
- DuckDB 自带的优化路径 `PerfectHashJoinExecutor`（针对稠密整型小范围主键的加速方案）适用范围窄（要求 build 侧是整型且取值范围在阈值内），且仍然依赖哈希表的构建与回表，实测加速效果有限。

**核心思路**：主外键连接本质上是"是否存在对应主键行"的**成员判断**问题，并不需要真正的哈希表。如果能提前把主键表编号成稠密整数（0、1、2…），外键表提前存好"指向这个编号"的引用列，那么：

- **Build 阶段**：只需要把出现过的主键编号，在一个位图（bitmap）里置 1，不需要建哈希表；
- **Probe 阶段**：直接用外键引用值去查位图对应的 bit，O(1) 判断是否匹配，不需要哈希计算和比较。

这就是本课题要落地的 **Bitmap HashJoin（简称 BHJ）**：用位图替代哈希表，在保证结果完全一致的前提下，降低多 HashJoin 查询的执行开销。

## 二、总体方案

整个方案分为"离线预处理"和"在线执行"两部分，并遵循**可开关配置、失败安全回退**的原则，确保不影响 DuckDB 现有功能的稳定性：

1. **离线预处理**：对参与主外键连接的维度表，额外生成一列稠密的 `rowid`（0 起递增）；对事实表，额外生成一列指向该 `rowid` 的引用列。这一步一次性完成，不影响原有数据。
2. **查询优化阶段（自动识别）**：如果开启open_bitmap_join优化选项，则在 DuckDB 原有优化器流程的最后新增一步，自动扫描查询计划里的每一个等值连接，判断它是否具备"主外键、build 侧唯一"的特征，符合条件的才会被标记为可以走 Bitmap 加速；不符合条件（比如复合条件、非主外键关系等）则完全不受影响，继续走原来的 HashJoin。
3. **执行阶段**：命中的连接改用位图完成匹配，跳过哈希表的构建与探测；未命中的连接行为与原生 DuckDB 完全一致。
4. **安全兜底**：任何环节（数据未预处理、查询形态不支持、统计信息导致主外键位置颠倒等）出现不确定性，都会自动、安静地回退到原生 HashJoin，不会报错、不会产生错误结果——这是本课题在设计上最看重的一条原则。

## 三、当前进展

### 3.1 已完成的能力

| 阶段 | 完成内容 |
| --- | --- |
| 基础能力搭建 | 完成开关机制（可随时整体关闭，零风险接入生产代码）、位图执行器原型、单个连接节点的手工验证 |
| **自动化识别**（本轮重点） | 查询优化器新增自动识别步骤：**无需人工干预**即可自动判断一个连接是否符合主外键关系、自动判断哪一侧是维度表（避免了此前"外键表被误判为维度表"这一潜在的运行期风险） |
| **隐藏列自动传播** | 支持维度表主键本身不是稠密整数的场景（更贴近真实业务，如订单表用订单号做主键）；支持这类"隐藏列"自动穿透 `WHERE` 过滤、子查询列裁剪、以及多层连接组成的复杂查询链路，且不会泄漏到用户最终看到的结果里 |
| **端到端验收基础设施** | 搭建了标准 TPC-H Q5 / Q9 / Q10 的自动化测试：分别在"原生 HashJoin / DuckDB 自带优化 / 本课题 Bitmap 优化"三种模式下运行，自动比对结果一致性，并输出耗时和命中率数据 |
| 正确性回归 | 新增单元测试用例（含自连接、同名列冲突、多次重复查询等边界场景），叠加 DuckDB 原有优化器回归测试，**全部通过**，未引入功能性缺陷 |

### 3.2 初步性能与命中率数据（TPC-H SF5）

| 查询 | 总 HashJoin 数 | 命中 Bitmap 加速数 | baseline 耗时 | 本方案耗时 |
| --- | --- | --- | --- | --- |
| Q5 | 5 | 3 | 160.6 ms | 151.6 ms |
| Q9 | 5 | 3 | 339.4 ms | 313.5 ms |
| Q10 | 3 | 1 | 219.3 ms | 218.5 ms |

**初步结论**：

- 正确性：三种模式结果完全一致，方案是安全、可用的；
- 性能：Q5/Q9 有小幅提升（约 5%~8%），Q10 基本持平；
- **命中率还未达到理论上限**：三条查询里符合条件的连接，目前只有一部分hashjoin被优化（Q10 更低，仅 1/3），这是当前收益不够显著的主要疑点，也是下一阶段的核心工作。

## 四、待解决的问题与下一步计划

结合对现有结果的复盘，识别出两方面需要继续推进的工作：

**1）更细致的性能分析和bitmapjoin优化（诊断）**
- 逐条分析 Q5/Q9/Q10 里每一个未命中的连接，区分"本来就不该命中"（如连接条件本身不满足要求，属于设计边界内，不算问题）和"本可以命中但目前被限制放弃"（属于可优化空间）；
- 扩展tpcds等benchmark，搜索更复杂、join占比的sql，并且对于查询结果需要单独profling并分析join 单operator的优化效果。

**2）优化scan operator（实现）**
- scan在整个sql查询中占比更高，初期分析，在对parquet格式数据查询时，大部分scan占比40%～80%，有更大的优化空间；
- 目前已对scan operator+gpu的优化做了详细设计，但预期ssd-内存-gpu这条单一路径的优化有限（现有环境无法使用GDS技术），后续scan-gpu路径搭建后需要与其他operator做深度优化以发挥gpu的性能。
